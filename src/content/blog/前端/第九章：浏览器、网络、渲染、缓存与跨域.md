# 三、浏览器不是只有一个进程

普通回答：

> 浏览器拿到 HTML 后解析页面。

深度回答要先知道，现代浏览器通常由多个进程协作。

## 1. 浏览器进程

主要负责：

- 地址栏和浏览器界面
- 标签页管理
- 页面导航
- 权限管理
- 与其他进程协调

## 2. 网络进程

主要负责：

- DNS 查询
- 网络连接
- HTTP 请求
- 缓存读取
- 下载资源

## 3. 渲染进程

主要负责：

- HTML 解析
- CSS 解析
- JavaScript 执行
- DOM 构建
- 样式计算
- 布局
- 绘制

渲染进程通常运行在沙箱中，以降低网页代码直接影响操作系统的风险。

## 4. GPU 进程

主要负责：

- 图层合成
- 部分图形加速
- 将图层结果交给显示设备

## 🔴 面试加分答案

> 浏览器是多进程架构。浏览器进程负责导航和界面管理，网络进程负责请求与缓存，渲染进程负责 HTML、CSS、JavaScript 和页面渲染，GPU 进程参与图层合成。JavaScript 主线程主要位于渲染进程中，所以长 JavaScript 任务会同时影响用户交互和页面渲染。

# 四、从输入 URL 到页面展示

假设输入：

```text
https://www.example.com/users?id=1#detail
```

URL 可以拆成：

| 部分     | 示例              | 作用                 |
| -------- | ----------------- | -------------------- |
| 协议     | `https`           | 使用什么通信协议     |
| 主机名   | `www.example.com` | 要访问哪台服务       |
| 端口     | 默认443           | 服务监听端口         |
| 路径     | `/users`          | 请求哪个资源         |
| 查询参数 | `id=1`            | 传递请求参数         |
| Hash     | `#detail`         | 通常只在浏览器端使用 |

注意：

> Hash 通常不会随普通 HTTP 请求发送给服务器。

------

## 完整流程

```text
输入 URL
→ 浏览器解析 URL
→ 判断是否能使用缓存
→ 查找 DNS，获得服务器 IP
→ 建立网络连接
→ HTTPS 完成 TLS 握手
→ 发送 HTTP 请求
→ CDN、网关或服务器处理请求
→ 返回 HTTP 响应
→ 浏览器解析 HTML
→ 请求 CSS、JavaScript、图片、字体
→ 构建 DOM 与 CSSOM
→ 生成渲染树
→ Layout 布局
→ Paint 绘制
→ Composite 合成
→ 页面显示
```

真实浏览器会并行、缓存和预测性地执行其中许多步骤，不是严格一项结束才开始下一项。

------

# 五、浏览器解析 URL 后会先做什么

## 1. 判断输入的是 URL 还是搜索词

输入：

```text
github.com
```

浏览器可能补全协议。

输入：

```text
学习 React
```

浏览器通常将其交给搜索引擎。

## 2. 检查 HSTS 等安全策略

某些站点会要求浏览器以后只能通过 HTTPS 访问。

即使输入：

```text
http://example.com
```

浏览器也可能直接升级到 HTTPS。

## 3. 检查缓存和 Service Worker

在真正发送网络请求前，浏览器可能：

- 查询内存缓存
- 查询磁盘缓存
- 交给 Service Worker 拦截
- 根据缓存策略决定是否请求服务器

具体顺序会受资源类型、导航类型和浏览器实现影响，但核心思想是：

> 发请求前不一定真的访问网络。

------

# 六、DNS：把域名转换成 IP

浏览器不能直接使用：

```text
www.example.com
```

访问服务器，需要先知道对应的 IP 地址。

DNS 类似互联网的电话簿：

```text
www.example.com
→ 93.184.216.34
```

------

## 1. DNS 查询大致顺序

浏览器通常会依次检查：

```text
浏览器 DNS 缓存
→ 操作系统 DNS 缓存
→ hosts 文件
→ 本地 DNS 解析器
→ 根域名服务器
→ 顶级域服务器
→ 权威 DNS 服务器
```

实际查询可能因缓存命中而大幅简化。

------

## 2. 常见 DNS 记录

| 类型  | 含义               |
| ----- | ------------------ |
| A     | 域名指向 IPv4 地址 |
| AAAA  | 域名指向 IPv6 地址 |
| CNAME | 域名指向另一个域名 |
| MX    | 邮件服务器记录     |
| TXT   | 文本配置和验证信息 |

CDN 经常借助 CNAME：

```text
static.example.com
→ CDN 分配的域名
→ 距离用户较近的 CDN 节点
```

------

## 3. DNS 优化方式

- DNS 缓存
- 减少不同域名数量
- `dns-prefetch`
- `preconnect`
- CDN 智能解析

## 🔴 标准答案

> DNS 负责把域名解析成服务器 IP。浏览器会先查本地多级缓存，未命中时再通过递归或迭代查询获得结果。DNS 结果可以被缓存，CDN 也会利用 DNS 将用户调度到距离较近或负载较低的节点。

------

# 七、TCP 为什么需要三次握手

获得 IP 后，HTTP/1.1 和 HTTP/2 通常需要先建立 TCP 连接。

TCP 三次握手可以简化为：

```text
客户端：我想建立连接，我的初始序号是 x
服务器：收到，我也同意连接，我的初始序号是 y
客户端：收到你的确认，连接建立
```

## 为什么不是两次

两次只能让服务器确认：

- 客户端发消息的能力正常
- 服务器接收能力正常

第三次让服务器知道：

- 客户端也能够接收服务器的响应
- 客户端确实收到了服务器的确认
- 双方初始序号同步完成

## 🔴 标准答案

> TCP 三次握手的核心是确认双方的发送和接收能力，并同步初始序号。两次握手不足以让服务器确认客户端是否成功收到了自己的确认，也可能受到历史失效连接请求影响，因此需要第三次确认。

------

# 八、HTTPS 和 TLS

HTTPS 可以理解为：

```text
HTTP
+
TLS 加密层
```

TLS 主要解决三个问题：

## 1. 机密性

传输内容被加密，旁观者不能轻易直接读取。

## 2. 完整性

传输内容被篡改时可以被发现。

## 3. 身份认证

通过证书验证访问的服务器是不是目标服务器。

------

## TLS 握手简化流程

```text
客户端发送支持的 TLS 版本和加密套件
→ 服务器返回证书和选择结果
→ 客户端验证证书
→ 双方协商出会话密钥
→ 后续使用对称加密传输 HTTP 数据
```

为什么后续主要使用对称加密？

因为：

- 非对称加密适合身份认证和密钥交换
- 对称加密速度更快，适合大量数据传输

## 🔴 高分答案

> HTTPS 不是简单地给 HTTP 内容加密。TLS 同时提供身份认证、数据加密和完整性校验。握手阶段利用证书和非对称密码体系建立信任并协商密钥，后续数据通常使用效率更高的对称加密传输。

------

# 九、HTTP 请求包含什么

一个 HTTP 请求大致包含：

```text
请求行
请求头
空行
请求体
```

例如逻辑结构：

```text
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer xxx

{"name":"刘凤伟"}
```

## 常见请求头

| 请求头              | 作用                   |
| ------------------- | ---------------------- |
| `Host`              | 目标主机               |
| `Content-Type`      | 请求体数据格式         |
| `Accept`            | 希望服务器返回什么格式 |
| `Authorization`     | 身份凭证               |
| `Cookie`            | 浏览器携带的 Cookie    |
| `User-Agent`        | 客户端信息             |
| `Referer`           | 请求来源页面           |
| `Origin`            | 请求源                 |
| `If-None-Match`     | 携带 ETag 进行协商缓存 |
| `If-Modified-Since` | 携带资源修改时间       |

# 十、常见 HTTP 状态码

## 2xx：成功

| 状态码 | 含义                         |
| ------ | ---------------------------- |
| 200    | 请求成功                     |
| 201    | 创建成功                     |
| 204    | 成功但没有响应体             |
| 206    | 返回部分内容，常见于范围请求 |

## 3xx：重定向和缓存

| 状态码 | 含义                         |
| ------ | ---------------------------- |
| 301    | 永久重定向                   |
| 302    | 临时重定向                   |
| 304    | 协商缓存命中，资源未修改     |
| 307    | 临时重定向，通常保留请求方法 |
| 308    | 永久重定向，通常保留请求方法 |

## 4xx：客户端相关问题

| 状态码 | 含义                 |
| ------ | -------------------- |
| 400    | 请求参数或格式错误   |
| 401    | 未认证或认证失效     |
| 403    | 已识别身份，但无权限 |
| 404    | 资源不存在           |
| 405    | 请求方法不允许       |
| 409    | 资源冲突             |
| 429    | 请求过于频繁         |

## 5xx：服务端问题

| 状态码 | 含义                 |
| ------ | -------------------- |
| 500    | 服务端内部错误       |
| 502    | 网关收到无效上游响应 |
| 503    | 服务暂时不可用       |
| 504    | 网关等待上游超时     |

## ⚠️ 高频陷阱

`401` 和 `403`：

> 401 更偏向“你还没有有效证明自己是谁”；403 更偏向“我知道你是谁，但你没有权限”。

# 十一、HTTP/1.1、HTTP/2 和 HTTP/3

## 1. HTTP/1.1

主要特点：

- 支持持久连接
- 一个 TCP 连接可以处理多个请求
- 支持管线化，但实践中使用受限
- 多个请求通常依赖多个 TCP 连接提高并发
- 存在队头阻塞问题

### 队头阻塞

同一个连接中的前一个响应没有完成时，后面的响应可能被影响。

浏览器通常会对同一域名建立多个 TCP 连接缓解问题，但连接过多也有成本。

------

## 2. HTTP/2

主要能力：

### 二进制分帧

HTTP 消息被拆成二进制帧进行传输。

### 多路复用

同一条 TCP 连接中，可以并行传输多个请求和响应。

### 头部压缩

减少重复请求头带来的传输开销。

### 流优先级等机制

允许对不同资源流进行管理。

但是 HTTP/2 仍运行在 TCP 上。

如果底层 TCP 丢包，多个 HTTP/2 流都可能等待重传，仍存在 TCP 层的队头阻塞。

------

## 3. HTTP/3

HTTP/3 基于 QUIC，QUIC 通常运行在 UDP 之上。

主要优势：

- 更快建立连接
- 流之间更加独立
- 一个流丢包不一定阻塞其他流
- 连接迁移能力更好
- TLS 安全能力集成在 QUIC 中

## 🔴 标准答案

> HTTP/1.1 通过持久连接减少重复建连，但多请求并发能力有限。HTTP/2 使用二进制分帧和多路复用，让多个请求共享一个 TCP 连接，并进行头部压缩；但底层 TCP 丢包仍可能影响多个流。HTTP/3 基于 QUIC，将不同流更好地隔离，减少 TCP 层队头阻塞，并改善连接建立和网络切换体验。

------

# 十二、浏览器拿到 HTML 后发生什么

网络响应到达后，浏览器并不是等整个 HTML 下载完再开始。

通常可以：

```text
边下载
→ 边解析
→ 边发现子资源
→ 边发起请求
```

------

# 十三、HTML 解析与 DOM

浏览器的 HTML 解析器会将 HTML 转换成 DOM 树。

HTML：

```html
<div><p>Vue</p></div>
```

逻辑 DOM：

```text
Document
└── html
    └── body
        └── div
            └── p
                └── 文本 Vue
```

DOM 主要描述：

- 页面有哪些节点
- 节点之间的父子关系
- 节点属性和文本内容

------

# 十四、CSS 解析与 CSSOM

CSS：

```css
.title {
  color: red;
}
```

会被浏览器解析成 CSSOM。

CSSOM 描述：

- 有哪些样式规则
- 选择器匹配什么元素
- 样式层叠和继承关系

CSSOM 构建完成后，浏览器才能更准确地计算每个元素最终应该使用什么样式。

------

# 十五、Render Tree 渲染树

渲染树不是简单地等于 DOM 树。

渲染树由：

```text
需要显示的 DOM 节点
+
节点最终计算样式
```

组成。

例如：

```css
.hidden {
  display: none;
}
```

`display: none` 的节点通常不会进入渲染树。

但是：

```css
.invisible {
  visibility: hidden;
}
```

节点仍然占据布局空间，所以仍参与布局。

## 🔴 三棵树区别

> DOM 表示文档结构，CSSOM 表示样式规则，Render Tree 表示实际参与页面布局和绘制的可见节点及其计算样式。

------

# 十六、浏览器渲染流水线

页面展示可以简化为：

```text
Style 样式计算
→ Layout 布局
→ Paint 绘制
→ Composite 合成
```

------

## 1. Style 样式计算

浏览器根据：

- CSS 选择器
- 层叠规则
- 继承
- 默认样式

确定每个节点最终样式。

例如：

```text
color 最终是什么
display 最终是什么
font-size 最终是什么
```

------

## 2. Layout 布局，也叫重排

计算元素的几何信息：

- 宽度
- 高度
- 位置
- 盒模型
- 父子布局关系

例如修改：

- `width`
- `height`
- `margin`
- `padding`
- `font-size`
- DOM 结构

可能影响 Layout。

------

## 3. Paint 绘制

把节点绘制成像素指令：

- 文字
- 背景
- 边框
- 阴影
- 图片

绘制不一定直接完成最终屏幕显示，而是形成绘制记录或图层内容。

------

## 4. Composite 合成

浏览器将多个图层按照顺序组合成最终页面。

经常只影响合成的属性包括：

- `transform`
- `opacity`

因此动画通常推荐优先使用：

```text
transform
opacity
```

而不是频繁修改：

```text
left
top
width
height
```

------

# 十七、重排、重绘和合成

## 1. 重排 Reflow / Layout

元素几何信息变化，需要重新计算布局。

例如：

- 改变宽高
- 插入 DOM
- 删除 DOM
- 字体变化
- 窗口尺寸变化

重排通常可能影响周围节点，成本较高。

## 2. 重绘 Repaint

几何结构没有变化，但视觉样式发生变化。

例如：

- 颜色变化
- 背景变化
- 阴影变化

通常不需要重新布局，但需要重新绘制。

## 3. 合成 Composite

如果变化只发生在独立合成层中，可以只重新组合图层。

一般成本更低。

## 大致成本关系

```text
重排 + 重绘 + 合成
>
重绘 + 合成
>
仅合成
```

这不是绝对固定的性能公式，但可以作为理解模型。

------

# 十八、强制同步布局

浏览器会尝试批量处理样式修改。

但如果代码刚修改样式，马上读取布局信息，浏览器为了返回准确值，可能被迫立即执行布局计算。

错误示例：

```js
const items = document.querySelectorAll('.item'); // 获取全部列表元素

items.forEach((item) => { // 遍历每一个列表元素
  item.style.width = `${item.offsetWidth + 10}px`; // 先读取布局，再立即写入样式，可能反复触发布局
}); // 元素遍历结束
```

上面每轮都可能出现：

```text
读取 offsetWidth
→ 浏览器确保布局是最新的
→ 修改 width
→ 布局失效
→ 下一轮再次读取
```

这叫布局抖动或 Layout Thrashing。

------

## 更好的写法：先统一读取，再统一写入

```js
const items = [...document.querySelectorAll('.item')]; // 获取元素并转换成普通数组

const widths = items.map((item) => { // 第一阶段统一读取布局信息
  return item.offsetWidth; // 读取每个元素当前宽度
}); // 布局读取结束

items.forEach((item, index) => { // 第二阶段统一修改样式
  item.style.width = `${widths[index] + 10}px`; // 根据之前读取的宽度更新样式
}); // 样式修改结束
```

## 🔴 面试加分答案

> 浏览器会尽量批量处理样式修改，但读取 `offsetWidth`、`getBoundingClientRect` 等布局信息时，为了返回准确结果，可能强制刷新之前积压的样式和布局。高频循环中交替读写会形成布局抖动，因此应该批量读取，再批量写入。

------

# 十九、JavaScript 如何影响 HTML 解析

经典普通脚本：

```html
<script src="./main.js"></script> <!-- 普通脚本下载和执行可能阻塞 HTML 继续解析 -->
```

浏览器解析到普通脚本时，通常需要：

```text
暂停 HTML 解析
→ 下载 JavaScript
→ 执行 JavaScript
→ 继续解析 HTML
```

因为 JavaScript 可能执行：

```js
document.write(); // JavaScript 可能直接修改当前正在解析的文档结构
```

------

# 二十、async 和 defer

## 1. 普通脚本

```html
<script src="./main.js"></script> <!-- 下载并执行脚本时通常阻塞 HTML 解析 -->
```

## 2. async

```html
<script async src="./analytics.js"></script> <!-- 脚本下载完成后立即执行，执行时可能阻塞解析，多个 async 脚本不保证顺序 -->
```

特点：

- 下载过程不阻塞 HTML 解析
- 下载完成后尽快执行
- 执行时可能暂停解析
- 多个脚本执行顺序不确定
- 适合独立脚本

例如：

- 统计脚本
- 广告脚本
- 与页面主逻辑无依赖的脚本

## 3. defer

```html
<script defer src="./vendor.js"></script> <!-- 异步下载，等待 HTML 解析完成后执行，并保持 defer 脚本顺序 -->
<script defer src="./main.js"></script> <!-- vendor.js 通常先于 main.js 执行 -->
```

特点：

- 下载不阻塞 HTML 解析
- HTML 解析完成后执行
- 多个 defer 脚本保持文档顺序
- 通常在 `DOMContentLoaded` 前执行
- 适合有依赖关系的页面主脚本

## 4. type="module"

```html
<script type="module" src="./main.js"></script> <!-- 模块脚本默认具有类似 defer 的加载执行行为 -->
```

模块脚本通常默认延迟执行，并支持：

- `import`
- `export`
- 模块作用域
- 依赖分析

## 📌 记忆

> async 是“谁先下载完谁先执行”，defer 是“下载可以并行，但按文档顺序，HTML 解析完再执行”。

------

# 二十一、CSS 会不会阻塞 HTML 解析

严谨回答：

> CSS 下载通常不会直接阻塞 HTML 解析器继续构建 DOM，但会阻塞页面渲染；同时，如果后面的 JavaScript 可能读取样式，脚本执行可能需要等待前面的 CSS 完成，从而间接延迟 HTML 解析。

为什么 CSS 阻塞渲染？

浏览器不希望：

```text
先按无样式页面显示
→ CSS 到达后再突然重排和闪动
```

所以关键 CSS 应尽快加载。

------

# 二十二、预加载扫描器

浏览器主 HTML 解析器遇到脚本而暂停时，通常还有预加载扫描器继续快速扫描后续内容，提前发现：

- CSS
- JavaScript
- 图片
- 字体

并提前发起请求。

这能减少纯串行下载。

但如果资源地址必须依赖 JavaScript 执行后才生成，预加载扫描器就可能无法提前发现。

## 🟡 面试加分

> 浏览器不仅依赖主 HTML 解析器发现资源，还可能使用预加载扫描器提前扫描后续标签并请求资源。但通过 JavaScript 动态生成的资源，通常更难被早期发现，因此关键资源应该尽量在 HTML 中明确声明。

------

# 二十三、DOMContentLoaded 和 load

## DOMContentLoaded

通常表示：

- HTML 已经解析完成
- DOM 已经构建完成
- defer 脚本已经执行

但不一定等待：

- 所有图片
- 视频
- 部分异步资源

## load

通常表示页面及其依赖资源加载完成，包括图片等资源。

## 例子

```js
document.addEventListener('DOMContentLoaded', () => { // 监听 DOM 结构解析完成
  console.log('DOM 已经可以使用'); // 输出 DOM 可用提示
}); // DOMContentLoaded 监听结束

window.addEventListener('load', () => { // 监听页面和资源加载完成
  console.log('页面主要资源已加载完成'); // 输出资源完成提示
}); // load 监听结束
```

------

# 二十四、浏览器缓存完整体系

浏览器缓存主要目标：

- 减少网络请求
- 减少响应数据传输
- 降低服务器压力
- 提升页面加载速度

面试重点分成：

```text
强缓存
+
协商缓存
```

------

# 二十五、强缓存

强缓存命中时：

> 浏览器直接使用本地资源，不向服务器确认资源是否变化。

主要响应头：

```text
Cache-Control
Expires
```

现代项目通常优先使用 `Cache-Control`。

------

## Cache-Control 常见值

### max-age

```text
Cache-Control: max-age=31536000
```

表示资源在指定秒数内可以被视为新鲜。

### no-cache

名字很容易误解。

`no-cache` 不是“不缓存”，而是：

> 可以保存缓存，但每次使用前必须向服务器重新验证。

### no-store

表示：

> 不要存储该响应。

适合高度敏感或不应缓存的内容。

### public

表示响应可以被浏览器和共享缓存存储。

### private

表示主要只允许私有客户端缓存，不希望共享缓存保存。

### immutable

表示资源有效期内不会改变，浏览器可减少重新验证。

------

## 🔴 高频陷阱

```text
no-cache ≠ 不缓存
no-store = 不存储
```

------

# 二十六、协商缓存

强缓存过期后，浏览器可以带上资源标识询问服务器：

> 我本地的资源还能继续用吗？

服务器判断资源没变：

```text
返回 304
不返回完整资源体
浏览器继续使用本地缓存
```

------

## 1. Last-Modified

服务器响应：

```text
Last-Modified: Wed, 30 Jul 2026 10:00:00 GMT
```

浏览器下次请求：

```text
If-Modified-Since: Wed, 30 Jul 2026 10:00:00 GMT
```

服务器比较修改时间：

- 没变化：返回 304
- 有变化：返回 200 和新资源

### 局限

- 时间精度有限
- 文件内容没变但时间变化
- 文件快速多次修改可能判断不准确

------

## 2. ETag

服务器响应：

```text
ETag: "asset-v123"
```

浏览器下次请求：

```text
If-None-Match: "asset-v123"
```

服务器比较资源标识：

- 相同：304
- 不同：200 和新资源

ETag 通常比修改时间更精确。

但生成和比较 ETag 也会有一定服务端成本。

------

## 3. ETag 与 Last-Modified

两者同时存在时，服务器通常会优先依据 ETag 相关条件进行判断。

## 🔴 标准答案

> 强缓存通过 Cache-Control 或 Expires 判断资源是否仍然新鲜，命中后不发送网络请求。强缓存失效后可以进入协商缓存，浏览器通过 If-None-Match 或 If-Modified-Since 向服务器验证资源。资源未变化时服务器返回 304，浏览器继续使用本地缓存；发生变化则返回 200 和新资源。

------

# 二十七、完整缓存判断流程

```text
请求资源
→ 检查是否有可用缓存
→ 强缓存是否仍然新鲜
    → 是：直接使用本地缓存
    → 否：发送条件请求
→ 服务器检查 ETag 或修改时间
    → 未变化：304，继续使用缓存
    → 已变化：200，返回新资源
```

开发者工具中可能看到：

- `from memory cache`
- `from disk cache`
- 304

## 内存缓存

- 读取速度快
- 生命周期通常较短
- 标签页关闭后可能消失

## 磁盘缓存

- 读取比内存慢
- 容量更大
- 可以跨页面和部分浏览器会话复用

具体采用哪一种由浏览器决定，业务代码通常不能精确控制。

------

# 二十八、前端项目最合理的缓存策略

## 1. HTML

通常不建议设置超长强缓存。

因为 HTML 决定要加载哪个 JavaScript 和 CSS 文件。

常见策略：

```text
HTML
→ no-cache
→ 每次向服务器验证
```

## 2. 带内容 Hash 的静态资源

例如：

```text
app.a8f921.js
style.193abc.css
```

内容变化时，文件名也变化。

因此可以设置：

```text
Cache-Control: public, max-age=31536000, immutable
```

旧文件可以长期缓存，新版本 HTML 会引用新文件名。

## 3. 图片和字体

对于带版本号或 Hash 的资源，也可以设置长期缓存。

## 4. API 接口

需要根据业务判断：

- 用户信息是否允许缓存
- 实时库存能否缓存
- 静态字典是否可以缓存
- 是否涉及权限和隐私
- 是否可能返回用户专属数据

## 🔴 项目满分答案

> 前端部署通常采用“HTML 短缓存或协商缓存，带内容 Hash 的 JavaScript、CSS 和图片长期强缓存”。HTML 每次验证后可以及时获得新资源地址；静态资源内容变化会生成新文件名，因此可以安全长期缓存。这样既保证版本更新，又提高二次访问速度。

------

# 二十九、为什么只改了代码，用户仍然看到旧页面

常见原因：

- HTML 被错误设置成长缓存
- Service Worker 缓存旧资源
- CDN 没有正确刷新
- 静态文件名没有 Hash
- 浏览器仍在使用旧资源
- 入口 HTML 引用了旧版本文件
- 多节点发布版本不一致

排查顺序：

```text
检查 HTML 响应头
→ 检查静态资源文件名
→ 检查 Network 的缓存来源
→ 检查 CDN 缓存
→ 检查 Service Worker
→ 检查服务器多实例版本
```

# 三十、Cookie、localStorage、sessionStorage、IndexedDB

## 1. Cookie

特点：

- 可以由服务器通过响应头设置
- 满足条件时会自动随请求发送
- 容量较小
- 支持过期时间
- 可设置 Domain 和 Path
- 可设置 `HttpOnly`
- 可设置 `Secure`
- 可设置 `SameSite`

适合：

- 会话标识
- 服务端认证
- 需要随请求自动发送的小型数据

不适合：

- 存放大量业务数据
- 存放复杂缓存
- 存放大 JSON

------

## 2. localStorage

特点：

- 同源下长期保存
- 浏览器关闭后通常仍存在
- 不会自动随请求发送
- API 是同步的
- JavaScript 可以直接访问
- 没有内置过期机制

```js
localStorage.setItem('theme', 'dark'); // 将主题配置保存到 localStorage

const theme = localStorage.getItem('theme'); // 读取之前保存的主题

localStorage.removeItem('theme'); // 删除保存的主题配置
```

同步 API 意味着：

> 大量频繁读写可能阻塞主线程。

------

## 3. sessionStorage

特点：

- API 与 localStorage 类似
- 通常以标签页会话为边界
- 标签页关闭后数据通常消失
- 不会自动随请求发送

适合：

- 当前标签页临时表单
- 页面跳转临时信息
- 一次会话中的临时状态

------

## 4. IndexedDB

特点：

- 异步
- 可以存储更大规模数据
- 支持对象和索引
- 适合结构化数据
- 不阻塞主线程式同步访问
- API 比 localStorage 复杂

适合：

- 离线数据
- 大量聊天记录
- 文件或 Blob
- 客户端数据库
- 大规模缓存

------

## 对比表

| 特性           | Cookie        | localStorage | sessionStorage | IndexedDB      |
| -------------- | ------------- | ------------ | -------------- | -------------- |
| 自动随请求发送 | 是            | 否           | 否             | 否             |
| 保存时间       | 可配置        | 长期         | 当前会话       | 长期           |
| API            | 浏览器/服务端 | 同步         | 同步           | 异步           |
| 容量           | 较小          | 中等         | 中等           | 较大           |
| 适合           | 会话认证      | 简单配置     | 标签页临时数据 | 大量结构化数据 |

# 三十一、Token 放哪里最安全

这是没有绝对统一答案的架构题。

## 放 localStorage

优点：

- 使用简单
- 请求时手动添加
- 不会自动随请求发送
- 相对不容易受到传统 CSRF 自动携带凭证影响

风险：

- 一旦发生 XSS，恶意脚本可以读取并窃取 Token

## 放 HttpOnly Cookie

优点：

- JavaScript 无法直接读取
- 能降低 Token 被脚本直接窃取的风险
- 服务端认证方便

风险：

- Cookie 可能自动随请求发送
- 需要配置 SameSite、CSRF Token 等防护
- XSS 虽然不能直接读 Cookie，但仍可能以当前用户身份发起操作

## 🔴 深度答案

> Token 存储要结合 XSS、CSRF、前后端架构和刷新机制综合设计。localStorage 不会自动携带，但容易被 XSS 读取；HttpOnly Cookie 无法被 JavaScript 读取，但要考虑 Cookie 自动携带带来的 CSRF 风险。无论选择哪种方案，都不能替代输入输出安全、CSP、SameSite、CSRF Token 和后端鉴权。

第十一章会详细学习。

------

# 三十二、同源策略

两个地址同源，需要三部分相同：

```text
协议
+
主机名
+
端口
```

例如当前页面：

```text
https://www.example.com:443
```

| 地址                            | 是否同源 | 原因       |
| ------------------------------- | -------- | ---------- |
| `https://www.example.com/users` | 是       | 三项相同   |
| `http://www.example.com`        | 否       | 协议不同   |
| `https://api.example.com`       | 否       | 主机名不同 |
| `https://www.example.com:8080`  | 否       | 端口不同   |

## 同源策略主要限制

- JavaScript 读取跨源响应
- 跨源 DOM 操作
- 部分跨源存储访问

注意：

> 跨源请求可能已经成功发送到服务器，只是浏览器不允许前端 JavaScript 读取响应。

------

# 三十三、CORS 是什么

CORS 全称：

> Cross-Origin Resource Sharing，跨源资源共享。

它是服务器通过响应头告诉浏览器：

> 这个来源可以读取我的响应。

常见响应头：

```text
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
Access-Control-Allow-Credentials
```

例如：

```text
Access-Control-Allow-Origin: https://www.example.com
```

表示只允许这个来源读取响应。

------

# 三十四、简单请求和预检请求

## 1. 简单请求

满足特定条件的跨域请求，可以直接发送实际请求。

通常包括：

- `GET`
- `HEAD`
- 某些 `POST`
- 仅使用允许的简单请求头
- Content-Type 属于允许范围

即使是简单请求，服务器仍需返回正确 CORS 响应头，浏览器才允许 JavaScript 读取响应。

------

## 2. 预检请求

当请求较复杂时，浏览器先发送 `OPTIONS`：

```text
我来自哪个 Origin
我准备使用什么请求方法
我准备携带什么请求头
服务器是否允许
```

服务器允许后，浏览器才发送实际请求。

常见触发场景：

- `PUT`
- `DELETE`
- 自定义请求头
- `Authorization`
- `application/json` 等非简单 Content-Type
- 某些复杂请求

## 预检不是业务代码手动发送

通常由浏览器自动完成。

------

# 三十五、跨域携带 Cookie

前端请求：

```js
const response = await fetch('https://api.example.com/user', { // 向跨域接口发送请求
  credentials: 'include', // 允许在符合条件时携带 Cookie
}); // fetch 请求配置结束
```

服务端需要返回类似：

```text
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Credentials: true
```

这时不能写：

```text
Access-Control-Allow-Origin: *
```

因为携带凭证时，服务器需要明确允许具体来源。

## 🔴 标准答案

> 跨域携带 Cookie 时，前端需要设置 credentials，服务端需要返回 Access-Control-Allow-Credentials: true，并指定明确的 Access-Control-Allow-Origin，不能使用通配符。Cookie 自身还要满足 Domain、Path、Secure 和 SameSite 等条件。

------

# 三十六、CORS 常见误区

## 误区一：CORS 阻止了请求发送

不一定。

部分跨域请求已经到达服务器，只是浏览器阻止 JavaScript 读取响应。

预检失败时，实际请求可能不会发送。

## 误区二：Postman 不跨域

更准确地说：

> 同源策略主要是浏览器安全机制，Postman 和服务端程序不受浏览器同源策略限制。

## 误区三：CORS 是权限认证

错误。

服务器允许某个 Origin 跨域读取响应，不代表用户就有业务权限。

仍然需要：

- Token
- Session
- 权限校验
- 数据范围校验

## 误区四：CORS 能防 CSRF

不能这样理解。

CORS 主要控制 JavaScript 是否能读取跨源响应，而 CSRF 利用的是浏览器自动携带凭证发起请求。

## 🔴 加分答案

> CORS 是浏览器和服务器之间的跨源读取授权机制，不是身份认证，也不是后端权限控制。攻击者可以绕过浏览器直接请求接口，所以服务端必须独立完成认证和授权。

------

# 三十七、开发代理为什么能解决跨域

开发时前端页面：

```text
http://localhost:5173
```

后端：

```text
https://api.example.com
```

浏览器直接请求会跨域。

配置开发代理后：

```text
浏览器请求 localhost:5173/api
→ Vite 开发服务器接收
→ Vite 服务器转发给 api.example.com
→ 浏览器看到的仍是 localhost:5173
```

因为浏览器只看到自己请求了同源开发服务器，所以没有前端跨域读取问题。

## ⚠️ 重要

开发代理只是开发环境方案。

生产环境仍需要：

- Nginx 反向代理
- 网关统一域名
- 服务端正确配置 CORS
- BFF

## 🔴 标准答案

> 开发代理不是修改浏览器同源策略，而是让浏览器只请求同源开发服务器，再由开发服务器以服务端身份转发到后端。服务端之间不受浏览器同源策略限制。生产环境需要网关、Nginx、BFF 或正确的 CORS 配置。

# 三十八、反向代理

用户请求：

```text
https://www.example.com/api/users
```

实际上由 Nginx 转发：

```text
/api
→ 后端接口服务
```

前端静态资源：

```text
/
→ 前端 HTML、JS、CSS
```

对浏览器来说：

```text
页面和接口都来自 www.example.com
```

因此可以避免跨域，并实现：

- 统一域名
- 负载均衡
- HTTPS 终止
- 缓存
- 压缩
- 接口转发
- 灰度发布

# 三十九、CDN 为什么能加速

CDN 全称：

> Content Delivery Network，内容分发网络。

没有 CDN：

```text
新加坡用户
→ 请求中国某个源服务器
→ 距离远、延迟高
```

使用 CDN：

```text
新加坡用户
→ 请求附近边缘节点
→ 边缘节点直接返回缓存资源
```

CDN 优势：

- 距离更近
- 降低网络延迟
- 分担源站压力
- 提高可用性
- 提供缓存和压缩
- 缓解突发流量

适合 CDN 的资源：

- JavaScript
- CSS
- 图片
- 字体
- 视频
- 公共下载文件

动态用户数据是否适合 CDN，需要结合权限、缓存键和数据新鲜度设计。

------

# 四十、CDN 回源

CDN 节点没有资源时：

```text
用户请求 CDN
→ CDN 缓存未命中
→ CDN 向源服务器请求
→ 源服务器返回
→ CDN 缓存资源
→ CDN 返回给用户
```

这叫回源。

需要关注：

- 缓存时间
- 缓存刷新
- 缓存版本
- 回源流量
- CDN 节点一致性
- Cookie 是否影响缓存

# 四十一、preload、prefetch、preconnect

## 1. preload

用于：

> 当前页面很快就需要的关键资源。

```html
<link rel="preload" href="/fonts/main.woff2" as="font" crossorigin /> <!-- 提前高优先级加载当前页面马上使用的字体 -->
```

适合：

- 首屏字体
- 首屏关键图片
- 关键脚本
- 关键 CSS

注意：

- 要设置正确的 `as`
- 跨域字体可能需要 `crossorigin`
- 预加载后必须真正使用
- 滥用会抢占关键带宽

------

## 2. prefetch

用于：

> 未来可能访问的页面资源。

```html
<link rel="prefetch" href="/assets/admin-page.js" /> <!-- 在浏览器空闲时预取未来可能使用的页面代码 -->
```

优先级通常较低。

适合：

- 下一页资源
- 用户可能访问的路由
- 非当前首屏必要资源

------

## 3. preconnect

用于提前完成：

- DNS
- TCP
- TLS

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin /> <!-- 提前与重要跨域资源服务器建立连接 -->
```

适合：

- 关键 CDN
- 字体服务器
- 重要第三方接口

不要对大量域名都 preconnect，因为连接本身也有成本。

------

## 4. dns-prefetch

只提前解析 DNS：

```html
<link rel="dns-prefetch" href="//cdn.example.com" /> <!-- 提前解析 CDN 域名对应的 IP -->
```

## 📌 记忆

> preload 是当前马上要用，prefetch 是以后可能要用，preconnect 是提前把路修好，dns-prefetch 是先查好地址。

# 四十三、Service Worker 缓存

Service Worker 可以作为浏览器与网络之间的可编程代理。

它可以：

- 拦截请求
- 自定义缓存策略
- 支持离线访问
- 后台同步
- 推送通知

常见缓存策略：

## Cache First

```text
先查缓存
→ 命中直接返回
→ 未命中再请求网络
```

适合长期不变的静态资源。

## Network First

```text
先请求网络
→ 网络失败再读缓存
```

适合需要较新数据的页面。

## Stale While Revalidate

```text
先快速返回旧缓存
→ 后台请求新资源
→ 更新缓存供下次使用
```

兼顾速度与新鲜度。

## ⚠️ 风险

Service Worker 缓存控制错误，可能导致：

- 用户长期看到旧版本
- 新旧资源混用
- 发布后难以刷新
- 缓存无限增长

所以版本管理和清理策略非常重要。

------

# 四十四、你的简历项目如何回答缓存优化

## 面试官：你如何设计前端缓存？

推荐回答：

> 我会区分入口 HTML、带 Hash 的静态资源和业务接口。HTML 使用短缓存或协商缓存，确保能及时获取最新资源清单；JavaScript、CSS、图片等带内容 Hash 的资源设置长期强缓存和 immutable，内容变化后文件名变化。对于分类、字典等低频接口，可以增加内存缓存或带过期时间的本地缓存；用户信息、库存和任务状态等实时或敏感数据则谨慎缓存。

------

## 面试官：为什么 JavaScript 可以缓存一年？

> 因为生产构建会为文件名添加内容 Hash。内容不变时 URL 不变，可以长期使用缓存；内容变化时 Hash 和 URL 改变，浏览器会请求新文件。因此长期缓存不会阻止版本更新，前提是入口 HTML 能及时更新并引用新的资源地址。

------

## 面试官：Gzip 是缓存吗？

> 不是。Gzip 或 Brotli 解决的是传输体积，缓存解决的是是否需要重复传输。首次请求可以通过压缩减少数据量，后续请求可以通过缓存避免传输，两者可以配合。

------

# 四十五、项目拷打：页面为什么白屏时间长

可以按关键路径分析：

```text
HTML 获取慢
→ DNS、连接、服务器响应问题

HTML 到了但 JS 下载慢
→ 包太大、缓存未命中、CDN 慢

JS 到了但执行慢
→ 长任务、框架初始化、第三方库过重

执行完但内容没出来
→ 接口串行、全局 loading、首屏依赖过多

内容出来但页面跳动
→ 图片未声明尺寸、字体替换、布局变化
```

## 高分回答

> 白屏不能只看接口耗时，要拆分成网络、资源下载、JavaScript 解析执行、框架挂载和数据渲染几个阶段，再通过 Network、Performance 和性能指标定位瓶颈。

# 四十六、项目拷打：跨域 403 是什么问题

不要直接回答：

> 这是 CORS。

403 和 CORS 不是一回事。

可能情况：

## 1. 服务端真的返回 403

原因可能是：

- 无权限
- Token 失效
- 来源校验失败
- 网关拒绝
- CSRF 校验失败
- 请求头或组织信息缺失

## 2. 预检 OPTIONS 返回 403

说明服务端或网关不允许当前跨域请求配置。

## 3. 响应缺少 CORS 头

服务器可能返回了业务响应，但浏览器不允许前端读取。

## 排查顺序

```text
查看 Network 中是否有 OPTIONS
→ 查看 OPTIONS 状态码
→ 查看实际请求是否发送
→ 查看响应中的 CORS 头
→ 查看 Token、Cookie、Origin
→ 查看网关和服务端日志
```

## 🔴 加分答案

> 跨域报错和 HTTP 403 要分开判断。先确认失败的是预检请求还是实际请求，再查看服务端是否返回正确 CORS 响应头。403 表示服务端或网关拒绝请求，可能是权限、来源、Token 或业务参数问题，不能一看到浏览器跨域提示就全部归因于 CORS。

# 四十七、从 URL 到页面展示的满分背诵答案

这段必须背熟：

> 用户输入 URL 后，浏览器先解析协议、主机、端口、路径和查询参数，并检查安全策略、缓存和 Service Worker。需要访问网络时，先通过 DNS 将域名解析为 IP，然后建立网络连接；HTTPS 还需要通过 TLS 验证服务器证书并协商加密密钥。
>
> 连接建立后，浏览器发送 HTTP 请求，服务器、网关或 CDN 处理后返回响应。浏览器拿到 HTML 后会边下载边解析，构建 DOM，并通过预加载扫描器提前发现 CSS、JavaScript、图片和字体等资源。CSS 被解析成 CSSOM，DOM 与计算样式共同形成渲染树。
>
> 浏览器随后进行样式计算、布局、绘制和图层合成，最终将页面显示到屏幕。普通 JavaScript 可能阻塞 HTML 解析，async 脚本下载完成后尽快执行且不保证顺序，defer 脚本在 HTML 解析完成后按顺序执行。
>
> 请求资源时，浏览器会先判断强缓存。强缓存命中则直接使用本地资源；失效后通过 ETag 或 Last-Modified 进行协商，资源未变化时服务器返回 304。生产项目通常让 HTML 使用短缓存或协商缓存，带内容 Hash 的静态资源使用长期强缓存。

------

# 四十八、本章最容易答错的 20 个点

1. 浏览器不是单进程架构。
2. JavaScript 主线程阻塞也会阻塞渲染和交互。
3. Hash 通常不发送给服务器。
4. 浏览器发送请求前可能先使用缓存或 Service Worker。
5. HTTPS 不只是加密，还包括认证和完整性。
6. HTTP/2 多路复用仍受 TCP 丢包影响。
7. 虚拟 DOM 不是浏览器渲染流程里的原生 DOM。
8. DOM、CSSOM、Render Tree 不是同一个概念。
9. `display:none` 节点通常不进入渲染树。
10. 重排通常会伴随重绘，但重绘不一定重排。
11. `transform`、`opacity` 更容易只触发合成。
12. 交替读取和写入布局可能造成布局抖动。
13. CSS 通常阻塞渲染，不应简单说完全阻塞 HTML 解析。
14. `async` 不保证脚本顺序。
15. `defer` 通常保持文档顺序。
16. `no-cache` 不等于不缓存。
17. 304 不会重新返回完整资源体。
18. localStorage 是同步 API。
19. CORS 不是身份认证。
20. 开发代理不能代替生产环境跨域方案。
