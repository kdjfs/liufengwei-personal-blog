# 一、性能优化的满分回答框架

面试官问：

> 你平时怎么做前端性能优化？

不要立刻开始背：

> CDN、Gzip、懒加载、Tree Shaking……

更好的开场是：

> 我会先明确优化目标和测量口径，再根据加载、交互、视觉稳定性、网络、JavaScript 执行和渲染几个阶段定位瓶颈。优化完成后在相同环境复测，并通过真实用户监控观察线上 P75 数据，避免只依赖本地 Lighthouse 单次结果。

性能优化的完整闭环是：

```text
1. 指标：到底慢在哪里
2. 归因：为什么慢
3. 方案：改什么
4. 代价：是否带来新问题
5. 复测：改善了多少
6. 监控：上线后是否发生回退
```

## 🔴 必背

> 性能优化不是优化项清单，而是以数据为依据的工程闭环。没有测量就无法确定瓶颈，没有统一口径就无法证明收益，没有线上监控就无法防止性能回退。

------

# 二、当前核心性能指标

目前 Core Web Vitals 的三个核心指标是：

```text
LCP：加载体验
INP：交互响应
CLS：视觉稳定性
```

FID 已被 INP 取代。官方建议使用真实访问数据的第 75 百分位进行评估，并分别观察移动端和桌面端。([web.dev](https://web.dev/articles/lcp?utm_source=chatgpt.com))

| 指标 | 良好       | 需要改进      | 较差       |
| ---- | ---------- | ------------- | ---------- |
| LCP  | ≤ 2.5 秒   | 2.5～4 秒     | > 4 秒     |
| INP  | ≤ 200 毫秒 | 200～500 毫秒 | > 500 毫秒 |
| CLS  | ≤ 0.1      | 0.1～0.25     | > 0.25     |

## 为什么看 P75

假设一百次访问：

- 50 个用户很快
- 25 个用户一般
- 25 个用户非常慢

只看平均值，慢用户可能被快用户“平均掉”。

P75 更关注：

> 至少 75% 的真实访问是否达到目标。

# 三、LCP：用户什么时候看到主要内容

LCP 全称：

> Largest Contentful Paint，最大内容绘制。

它关注首屏可视区域中最大图片、文本块或视频等主要元素何时完成绘制。([web.dev](https://web.dev/articles/lcp?hl=en&utm_source=chatgpt.com))

例如旅游首页中，LCP 元素可能是：

- 首屏大图
- 行程主标题
- 大面积 Banner
- 首屏内容卡片
- 大段介绍文字

## 1. LCP 可以拆成四段

```text
TTFB
+
资源加载延迟
+
资源下载耗时
+
元素渲染延迟
```

官方 LCP 优化指南也强调，要区分资源发现、资源加载和元素最终渲染之间的等待。([web.dev](https://web.dev/articles/optimize-lcp?hl=en&utm_source=chatgpt.com))

### TTFB 慢

可能原因：

- DNS、网络距离
- 服务端处理慢
- 数据库查询慢
- SSR 渲染慢
- CDN 未命中
- 缓存策略不合理

### 资源加载延迟高

可能原因：

- LCP 图片由 JavaScript 执行后才发现
- 图片藏在 CSS 背景中
- 错误地对首屏图使用懒加载
- 关键资源优先级过低
- 前面有大量无关资源竞争带宽

### 资源下载慢

可能原因：

- 图片尺寸过大
- 未使用响应式图片
- 未压缩
- CDN 节点远
- 网络环境差

### 渲染延迟高

可能原因：

- JavaScript 长任务
- 客户端渲染必须等大包执行
- CSS 阻塞
- 字体等待
- 数据请求串行
- 全局 Loading 阻塞全部内容

# 四、如何优化 LCP

## 1. 让 LCP 资源尽早被发现

首屏大图最好直接出现在 HTML 中：

```html
<!-- 声明首屏核心图片，让浏览器尽早发现 -->
<img
  src="/images/hero.webp"
  width="1200"
  height="600"
  fetchpriority="high"
  alt="旅游首页首屏图片"
/>
```

代码逐行理解：

```text
src
→ 声明实际图片地址

width、height
→ 提前保留布局空间

fetchpriority="high"
→ 提示浏览器提高资源优先级
```

LCP 图片不应默认使用：

```html
<!-- 不推荐：首屏核心图片不应故意延迟加载 -->
<img
  src="/images/hero.webp"
  loading="lazy"
  alt="首页首图"
/>
```

对于浏览器无法早期发现的关键背景图，可以谨慎使用 `preload`；但预加载过多资源会争抢带宽，因此只应针对真正关键资源。([web.dev](https://web.dev/articles/preload-responsive-images?utm_source=chatgpt.com))

------

## 2. 使用响应式图片

```html
<!-- 根据设备宽度选择合适尺寸的图片 -->
<img
  src="/images/hero-1200.webp"
  srcset="
    /images/hero-480.webp 480w,
    /images/hero-800.webp 800w,
    /images/hero-1200.webp 1200w
  "
  sizes="100vw"
  width="1200"
  height="600"
  alt="旅行风景"
/>
```

这样手机不必下载桌面端的大图片。响应式图片能减少无意义字节传输，也有助于改善图片作为 LCP 元素时的加载表现。([web.dev](https://web.dev/articles/serve-responsive-images?hl=en&utm_source=chatgpt.com))

------

## 3. 减少渲染阻塞

首屏不是必须的资源：

- 地图 SDK
- ECharts
- 富文本编辑器
- 管理后台模块
- 低频弹窗
- AI 对话模块

不要全部塞进入口包。

应该：

```text
首屏必要代码
→ 立即加载

非首屏模块
→ 路由懒加载或交互后加载
```

------

# 五、INP：用户点了之后多久有反馈

INP 全称：

> Interaction to Next Paint，交互到下一次绘制。

它观察用户在页面上的点击、键盘输入等交互延迟，并用接近最差交互的结果反映整体响应性。([web.dev](https://web.dev/articles/inp?utm_source=chatgpt.com))

一次交互可以拆成：

```text
输入延迟
+
事件处理耗时
+
浏览器呈现延迟
```

## 1. 输入延迟

用户已经点击，但主线程还在执行其他任务。

```text
用户点击按钮
→ 主线程正在解析大段 JavaScript
→ 等待 300ms
→ 点击回调才开始执行
```

## 2. 事件处理耗时

回调本身太重：

```text
点击
→ 同步筛选十万条数据
→ 构建巨大树结构
→ 解析大量 Markdown
→ 更新大量状态
```

## 3. 呈现延迟

事件执行结束后，浏览器还要：

- React/Vue 更新
- 样式计算
- Layout
- Paint
- Composite

才能给用户看到结果。

------

# 六、Long Task 为什么影响 INP

浏览器开发工具通常把占用主线程超过 50 毫秒的任务视为 Long Task。长任务执行期间，点击和输入只能排队等待，页面可能看起来“点了没反应”。([web.dev](https://web.dev/articles/optimize-long-tasks?utm_source=chatgpt.com))

例如：

```js
function processLargeData(items) { // 定义大量数据处理函数
  return items.map((item) => { // 同步遍历全部数据
    return expensiveTransform(item); // 对每一项执行复杂计算
  }); // map 处理结束
} // processLargeData 函数结束
```

如果有十万项，这个同步任务可能长时间占用主线程。

------

# 七、拆分长任务

可以将一个大任务拆成多个小任务，并在批次之间让出主线程。

```js
function yieldToMainThread() { // 定义让出主线程的辅助函数
  return new Promise((resolve) => { // 返回一个等待后续宏任务的 Promise
    setTimeout(resolve, 0); // 将恢复逻辑放到后续任务中
  }); // Promise 创建结束
} // yieldToMainThread 函数结束

async function processInChunks( // 定义分片处理函数
  items, // 接收待处理数据
  chunkSize = 200, // 设置每批处理数量
) {
  const results = []; // 创建最终结果数组

  for ( // 按照固定批次遍历数据
    let startIndex = 0; // 从第零项开始
    startIndex < items.length; // 判断是否还有剩余数据
    startIndex += chunkSize // 每次移动一个批次
  ) {
    const endIndex = Math.min( // 计算当前批次结束位置
      startIndex + chunkSize, // 当前起点加批次大小
      items.length, // 不能超过数组总长度
    ); // 结束索引计算完成

    for ( // 遍历当前批次
      let currentIndex = startIndex; // 从当前批次起点开始
      currentIndex < endIndex; // 不超过当前批次末尾
      currentIndex += 1 // 每次处理下一项
    ) {
      results.push( // 将处理结果加入结果数组
        expensiveTransform(items[currentIndex]), // 转换当前数据
      ); // push 操作结束
    } // 当前批次遍历结束

    if (endIndex < items.length) { // 判断后面是否还有数据
      await yieldToMainThread(); // 暂时让出主线程处理输入和渲染
    } // 剩余数据判断结束
  } // 全部批次处理结束

  return results; // 返回完整处理结果
} // processInChunks 函数结束
```

## 这种方案的代价

- 总完成时间可能变长
- 批次太小会产生大量调度开销
- 批次太大仍会卡顿
- 需要结合设备性能调整

对于真正 CPU 密集型任务，更适合使用 Web Worker，而不是只在主线程不断分片。官方建议通过减少不必要 JavaScript、拆分长任务以及在适合时使用 Worker，降低主线程阻塞。([web.dev](https://web.dev/articles/optimize-inp?utm_source=chatgpt.com))

------

# 八、Web Worker 适合什么场景

适合：

- 大型 JSON 转换
- 图片处理
- 加密解密
- 大规模路径计算
- 复杂排序和聚合
- 文件解析
- 十万级数据运算

不适合：

- 直接操作 DOM
- 极小计算
- 每次都传输巨大对象
- 高频创建和销毁 Worker

## 🔴 标准答案

> 分片是让主线程在多个小任务之间获得响应机会，Web Worker 则是把 CPU 密集型计算真正移出主线程。选择时要考虑计算量、通信成本和数据传输成本。

# 九、CLS：页面为什么会突然跳动

CLS 全称：

> Cumulative Layout Shift，累积布局偏移。

它衡量页面内容是否在用户没有预期的情况下发生位置变化。良好 CLS 应不高于 0.1。([web.dev](https://web.dev/articles/cls?utm_source=chatgpt.com))

常见问题：

```text
用户准备点击“确认”
→ 顶部广告突然加载
→ 按钮向下移动
→ 用户误点“删除”
```

------

# 十、CLS 常见原因与解决办法

## 1. 图片没有声明尺寸

错误：

```html
<!-- 不推荐：加载前浏览器不知道图片要占多少空间 -->
<img
  src="/images/travel.webp"
  alt="旅行图片"
/>
```

正确：

```html
<!-- 推荐：提前为图片保留固定比例空间 -->
<img
  src="/images/travel.webp"
  width="800"
  height="600"
  alt="旅行图片"
/>
```

为图片声明尺寸可以显著减少图片加载后的布局变化。([web.dev](https://web.dev/articles/optimize-cls?hl=zh-cn&utm_source=chatgpt.com))

------

## 2. 骨架屏和真实内容尺寸不一致

错误：

```text
骨架屏高度 100px
→ 真实卡片高度 400px
→ 内容加载后页面整体下移
```

正确：

> 骨架屏应尽量模拟真实内容的尺寸和布局，而不只是放几个灰色方块。

------

## 3. 在现有内容上方插入内容

例如页面加载后突然在顶部插入：

- 广告
- 公告
- 权限提示
- 下载提示
- 错误横幅

应提前预留空间，或在不推动主要内容的位置展示。

------

## 4. 字体替换造成布局变化

网络字体与后备字体的字宽和行高差距过大时，字体加载后可能重新排版。

优化方式：

- 精简字体字形
- 选择尺寸接近的后备字体
- 合理使用 `font-display`
- 只预加载首屏关键字体
- 使用字体尺寸调整属性降低差异

字体加载策略与后备字体尺寸匹配会直接影响 CLS。([web.dev](https://web.dev/articles/optimize-cls?hl=zh-cn&utm_source=chatgpt.com))

# 十一、实验室数据和真实用户数据

## 实验室数据 Lab Data

工具包括：

- Lighthouse
- Chrome DevTools Performance
- WebPageTest
- 本地 Performance 面板

优点：

- 环境可控
- 方便复现
- 上线前就能测
- 适合定位问题

缺点：

- 只是模拟环境
- 无法覆盖真实设备和网络
- 单次结果可能有偶然性

## 真实用户数据 Field / RUM

来自真实用户访问。

能体现：

- 不同手机性能
- 不同网络质量
- 不同地区
- 不同缓存状态
- 不同操作习惯

Core Web Vitals 本质上更强调真实用户数据；Lighthouse 适合诊断，但不能完全替代 RUM。([web.dev](https://web.dev/articles/vitals-tools?utm_source=chatgpt.com))

## 🔴 必背

> Lighthouse 告诉我在模拟环境中哪里可能有问题，RUM 告诉我真实用户到底体验得怎么样。优化时两者要结合，而不能拿一次本地跑分作为最终结论。

# 十二、接入 Web Vitals 线上监控

官方推荐使用 `web-vitals` 库采集 LCP、INP、CLS，再发送到自己的分析系统。([web.dev](https://web.dev/articles/vitals?utm_source=chatgpt.com))

```js
import { // 从 web-vitals 中导入核心指标监听函数
  onCLS, // 导入 CLS 监听函数
  onINP, // 导入 INP 监听函数
  onLCP, // 导入 LCP 监听函数
} from 'web-vitals'; // web-vitals 导入结束

function reportWebVital(metric) { // 定义性能指标上报函数
  const payload = { // 构造需要上报的数据
    name: metric.name, // 保存指标名称
    value: metric.value, // 保存指标最终值
    rating: metric.rating, // 保存指标评级
    id: metric.id, // 保存本次指标唯一 ID
    delta: metric.delta, // 保存与上次上报相比的变化量
    path: window.location.pathname, // 保存当前页面路径
    userAgent: navigator.userAgent, // 保存用户设备信息
    release: '2026.07.31', // 保存当前前端发布版本
    timestamp: Date.now(), // 保存上报时间
  }; // 上报数据构造结束

  const body = new Blob( // 创建适合 sendBeacon 的请求体
    [JSON.stringify(payload)], // 将上报对象转换成 JSON 字符串
    {
      type: 'application/json', // 声明请求体为 JSON
    }, // Blob 配置结束
  ); // Blob 创建结束

  if (navigator.sendBeacon) { // 判断浏览器是否支持 sendBeacon
    navigator.sendBeacon( // 在不阻塞页面离开的情况下上报
      '/api/performance', // 设置性能上报接口
      body, // 传入上报请求体
    ); // sendBeacon 调用结束

    return; // sendBeacon 已处理时结束函数
  } // sendBeacon 支持判断结束

  void fetch('/api/performance', { // 不支持 sendBeacon 时使用 fetch 兜底
    method: 'POST', // 使用 POST 请求
    headers: { // 设置请求头
      'Content-Type': 'application/json', // 声明发送 JSON
    }, // 请求头设置结束
    body: JSON.stringify(payload), // 序列化上报数据
    keepalive: true, // 页面退出时尽量继续完成请求
  }); // fetch 上报结束
} // reportWebVital 函数结束

onLCP(reportWebVital); // 监听并上报 LCP

onINP(reportWebVital); // 监听并上报 INP

onCLS(reportWebVital); // 监听并上报 CLS
```

## 上报时还应携带什么

建议携带：

- 路由
- 前端版本
- 设备类型
- 网络类型
- 用户地区
- 是否命中缓存
- 匿名用户 ID
- 页面业务类型
- LCP 元素归因
- 交互元素归因

不能只记录：

```text
LCP = 4.2s
```

否则你知道慢，却不知道：

- 哪个页面慢
- 哪个版本开始慢
- 什么设备慢
- 哪个元素慢
- 是否集中在某个地区

# 十三、SPA 路由切换需要自定义指标

Core Web Vitals 通常围绕顶层页面导航计算，SPA 内部路由切换不会被自动当成一次全新的页面加载重新统计。([web.dev](https://web.dev/articles/vitals-spa-faq?utm_source=chatgpt.com))

因此 React/Vue 单页应用还应自定义：

- 路由切换耗时
- 页面数据可用时间
- 首屏卡片展示时间
- AI 首字时间
- 地图初始化时间
- 图表可交互时间

```js
function startRouteMeasure(routeName) { // 定义路由开始测量函数
  performance.mark( // 创建路由开始标记
    `${routeName}-start`, // 使用路由名生成标记名称
  ); // 开始标记结束
} // startRouteMeasure 函数结束

function endRouteMeasure(routeName) { // 定义路由结束测量函数
  performance.mark( // 创建路由结束标记
    `${routeName}-end`, // 使用路由名生成结束标记
  ); // 结束标记完成

  performance.measure( // 根据两个标记计算耗时
    `${routeName}-duration`, // 设置测量结果名称
    `${routeName}-start`, // 指定开始标记
    `${routeName}-end`, // 指定结束标记
  ); // measure 调用结束

  const entries = performance.getEntriesByName( // 读取对应测量结果
    `${routeName}-duration`, // 指定测量名称
  ); // 性能记录读取结束

  const latestEntry = entries.at(-1); // 获取最后一次测量结果

  console.log( // 输出本次路由切换耗时
    `${routeName} 路由耗时：`, // 输出说明文本
    latestEntry?.duration, // 输出持续时间
  ); // console.log 结束
} // endRouteMeasure 函数结束
```

真正结束的位置不应随便放在组件函数执行后，而应根据业务定义：

```text
路由开始
→ 组件代码加载完成
→ 核心接口返回
→ 核心区域渲染完成
→ 记录结束
```

# 十五、路由级代码分割

React：

```jsx
import { // 从 React 中导入懒加载与等待边界

  Suspense, // 导入异步组件等待组件
} from 'react'; // React API 导入结束

const TripResultPage = lazy(() => { // 定义懒加载行程结果页

    './pages/TripResultPage' // 指定需要异步加载的模块
  ); // 动态 import 结束
}); // lazy 配置结束

function App() { // 定义应用组件
  return ( // 返回应用界面
    <Suspense // 为异步页面提供加载状态

      } // fallback 配置结束

  ); // JSX 返回结束

```

# 十七、Tree Shaking 为什么有时失效

Tree Shaking 是构建工具删除未使用代码的过程，通常依赖 ES Module 的静态 `import` 和 `export` 结构。([webpack](https://webpack.js.org/guides/tree-shaking/?utm_source=chatgpt.com))

例如：

```js
import { // 从工具库中按需导入函数
  debounce, // 导入防抖函数
} from './utils.js'; // 工具模块导入结束
```

构建工具可以分析哪些导出没有被使用。

可能失效的原因：

- 使用 CommonJS 动态导入
- 模块存在副作用
- 整包默认导入
- 第三方库没有良好 ESM 构建
- `sideEffects` 配置错误
- 代码动态访问，难以静态分析

## ⚠️ `sideEffects: false` 不能乱写

某些模块导入后会自动：

- 注册全局组件
- 注入 CSS
- 修改原型
- 注册 Polyfill

错误标记为无副作用，构建工具可能把必要代码删掉。

# 二十二、大列表为什么要使用虚拟列表

假设接口返回一万条数据：

```text
接口返回很快
≠ 页面一定流畅
```

如果全部生成 DOM：

- 创建一万个节点
- 样式计算成本增大
- Layout 成本增大
- 内存占用增加
- 更新和滚动成本增加

虚拟列表只渲染：

```text
当前视口中的节点
+
前后少量缓冲节点
```

滚动时不断复用或替换可见区域内容。大型列表虚拟化可以显著降低同时存在的 DOM 数量和渲染工作。([web.dev](https://web.dev/articles/virtualize-long-lists-react-window?utm_source=chatgpt.com))

## 虚拟列表难点

- 固定高度容易
- 动态高度需要测量和缓存
- 快速滚动时避免白屏
- 保持滚动位置
- 列表增删后的高度修正
- 图片加载引起高度变化
- 无障碍和搜索能力

## 🔴 标准答案

> 分页减少一次获取的数据量，虚拟列表减少一次渲染的 DOM 数量。两者解决的问题不同，可以同时使用。

# 二十三、避免 Layout Thrashing

错误：

```js
const cards = document.querySelectorAll('.card'); // 获取全部卡片元素

cards.forEach((card) => { // 遍历每个卡片
  const currentHeight = card.offsetHeight; // 读取当前布局信息

  card.style.height = `${currentHeight + 10}px`; // 立即写入新的布局样式
}); // 卡片遍历结束
```

循环中不断：

```text
读取布局
→ 修改样式
→ 再读取布局
→ 再修改样式
```

可能触发强制同步布局。

正确思想：

```js
const cards = [ // 将 NodeList 转换成数组
  ...document.querySelectorAll('.card'), // 获取全部卡片
]; // 卡片数组创建结束

const heights = cards.map((card) => { // 第一阶段统一读取
  return card.offsetHeight; // 读取当前卡片高度
}); // 高度读取结束

cards.forEach((card, index) => { // 第二阶段统一写入
  card.style.height = `${ // 设置新的卡片高度
    heights[index] + 10 // 在旧高度基础上增加十像素
  }px`; // 高度字符串结束
}); // 样式写入结束
```

DOM 规模过大及读写交错导致的同步布局，会加重主线程工作并影响交互响应。([web.dev](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing?hl=en&utm_source=chatgpt.com))

# 二十四、动画为什么优先 transform 和 opacity

修改：

```text
width
height
left
top
margin
```

经常会影响布局。

修改：

```text
transform
opacity
```

更有机会仅在合成阶段处理。

错误：

```js
element.style.left = '300px'; // 修改 left 可能触发布局计算
```

推荐：

```js
element.style.transform = ( // 使用 transform 改变视觉位置
  'translateX(300px)' // 将元素向右移动三百像素
); // transform 设置结束
```

但不要绝对化：

> `transform` 也不是零成本；过多合成层会占用 GPU 内存和管理成本。

`will-change` 也不能给所有元素都加，只应针对即将发生变化的少量元素使用。

# 二十五、React 性能优化优先级

React 优化不要从 `useMemo` 开始。

正确顺序：

```text
1. 状态放到正确位置
2. 拆分更新边界
3. 避免重复派生状态
4. 减少大规模 DOM
5. 定位真正重渲染热点
6. 再使用 memo 化
```

## 1. 状态下沉

搜索框关键词只在搜索组件使用，就不要放在包含地图和图表的最顶层页面。

## 2. 拆分频繁更新区域

```text
TripResultPage
├── StaticOverview
├── MapPanel
├── BudgetPanel
└── StreamingChat
```

流式聊天更新时，不应让地图和预算模块跟着频繁重新计算。

## 3. React.memo

只对：

- 渲染确实昂贵
- props 大部分时间稳定
- 父组件频繁更新

的组件使用。

## 4. useMemo/useCallback

为了：

- 缓存昂贵计算
- 向 memo 子组件传稳定引用
- 保持订阅依赖稳定

而不是为了“代码看起来专业”。

# 二十八、长聊天和流式输出优化

你的生猪健康系统写了长会话分层加载和流式 Markdown 渲染，这部分很容易被面试官深挖。

## 常见错误架构

服务器每返回一个字符：

```text
setMessages
→ 创建新消息数组
→ 所有消息组件参与更新
→ 重新解析整段 Markdown
→ 重新执行 DOMPurify
→ 更新 DOM
→ 自动滚动
```

一秒几十次，消息越长越卡。

------

## 正确优化方向

### 1. 首屏只加载最近消息

```text
先加载最近 20 条
→ 首屏可快速使用
→ 用户向上滚动时再加载历史消息
```

### 2. 只更新最后一条消息

历史消息对象引用保持稳定。

### 3. 流式字符先进入缓冲区

不要每一个字符都立即进入 React State。

```jsx
import { // 从 React 中导入需要的 Hook
  useEffect, // 导入副作用 Hook
  useRef, // 导入可变引用 Hook
  useState, // 导入状态 Hook
} from 'react'; // React Hook 导入结束

function useStreamingMessage() { // 定义流式消息 Hook
  const [content, setContent] = useState(''); // 保存真正用于渲染的内容

  const bufferRef = useRef(''); // 保存尚未提交到 UI 的字符

  const frameIdRef = useRef(null); // 保存当前动画帧编号

  function appendChunk(chunk) { // 定义接收流式字符的方法
    bufferRef.current += chunk; // 先将字符追加到缓冲区

    if (frameIdRef.current !== null) { // 判断是否已经安排刷新
      return; // 已安排时不再重复创建动画帧
    } // 刷新任务判断结束

    frameIdRef.current = requestAnimationFrame(() => { // 下一帧批量更新 UI
      const pendingContent = bufferRef.current; // 读取当前缓冲的全部字符

      bufferRef.current = ''; // 清空已经读取的缓冲区

      frameIdRef.current = null; // 重置动画帧状态

      setContent((previousContent) => { // 使用最新状态进行函数式更新
        return previousContent + pendingContent; // 一次性追加本帧全部字符
      }); // content 更新结束
    }); // requestAnimationFrame 注册结束
  } // appendChunk 函数结束

  useEffect(() => { // 注册组件卸载清理
    return () => { // 返回清理函数
      if (frameIdRef.current !== null) { // 判断是否还有等待中的动画帧
        cancelAnimationFrame( // 取消未执行的动画帧
          frameIdRef.current, // 传入动画帧编号
        ); // 取消操作结束
      } // 动画帧判断结束
    }; // 清理函数结束
  }, []); // 只注册一次清理逻辑

  return { // 返回 Hook 对外能力
    content, // 返回当前展示内容
    appendChunk, // 返回追加流式字符的方法
  }; // 返回对象结束
} // useStreamingMessage Hook 结束
```

这个方案将：

```text
每个字符更新一次
```

变成：

```text
一帧最多提交一次
```

如果 Markdown 解析仍然很重，还可以降低到每几十毫秒提交一次。

------

## 4. 只解析变化消息

不要每次重新解析全部历史消息：

```text
100 条历史消息
+
最后一条流式消息变化
```

应只重新解析最后一条。

## 5. 虚拟化历史消息

超长会话不能无限保留全部 DOM。

## 6. 控制自动滚动

只有当用户本来就在底部附近时才自动跟随。

用户正在看历史消息时，不应强制把他拉回底部。

## 7. 区分首字时间和完整回答时间

AI 性能至少有两个指标：

```text
首字时间
→ 用户多久看到第一段回答

完整时间
→ 整个答案多久生成结束
```

流式输出可能没有缩短模型总生成时间，但显著降低了用户感知等待时间。

# 二十九、如何讲“4.2 秒降到 1.7 秒”

你的简历写了长会话响应由 4.2 秒下降到 1.7 秒。这个数字本身不是重点，重点是你能否说清口径和证据。

面试官可能追问：

- 4.2 秒测的是什么？
- 是平均值还是 P75？
- 测了多少次？
- 网络环境相同吗？
- 是首字时间还是完整加载时间？
- 是接口快了，还是页面先显示了？
- 1.7 秒怎么测出来的？

## 推荐回答结构

> 我先把指标定义为用户进入会话后，到最近一屏消息可见并且 AI 区域可以开始交互的时间，而不是所有历史记录全部加载完成的时间。基线在固定测试环境下多次测量约为 4.2 秒。

> 排查后发现主要问题不是单个接口特别慢，而是历史消息全量请求、串行依赖、完整 Markdown 解析和大批量 DOM 渲染都处于首屏关键路径。我把最近消息优先返回并渲染，历史消息改成向上分页；互不依赖的数据并行请求；流式内容分批更新，只重新解析最后一条消息；同时取消重复请求。

> 优化后相同口径下降到约 1.7 秒。这个结果代表首屏可用时间，并不代表全部历史消息和完整 AI 回答都在 1.7 秒完成。线上还应该继续观察 P75，而不是只看本地最好结果。

这段最加分的地方是：

> 主动区分首屏可用时间和完整任务完成时间。

# 三十、如何讲“4.5MB 降到 2.7MB”

你的简历还写了构建体积由 4.5MB 降至 2.7MB。

必须先说清楚：

```text
是源码大小？
是 dist 总大小？
是未压缩大小？
是 Gzip 后大小？
是首屏加载体积？
还是所有异步包总大小？
```

## 推荐回答

> 我先通过构建分析确认大体积主要来自哪些模块，并区分总体构建体积和首屏传输体积。然后将地图、图表和低频管理模块改为动态加载，清理未使用依赖，调整重复依赖，引入按需加载和 Tree Shaking，同时启用文本压缩。

> 最终 4.5MB 到 2.7MB 指的是同一构建口径下的产物大小。实际用户体验还要结合首屏请求的 chunk 数量、压缩后传输体积和 JavaScript 执行时间，不能只看 dist 文件夹总大小。

## 面试官最喜欢的追问

> 包变小了，但为什么页面还是慢？

回答：

> 因为包体积只是影响因素之一。页面还可能慢在 TTFB、缓存未命中、JavaScript 执行、接口串行、图片、字体和 DOM 渲染。甚至过度分包后，包总量变小但请求瀑布变长，也可能让首屏变慢，所以必须回到真实指标复测。

# 三十一、性能预算

团队可以提前设置性能预算，例如：

```text
首屏 JavaScript 压缩后不超过某个目标
LCP P75 不超过 2.5 秒
INP P75 不超过 200ms
CLS P75 不超过 0.1
单个路由异步包不超过某个目标
单张首屏图片不超过某个目标
```

具体体积值应结合业务和用户设备制定，不能所有项目使用同一个数字。

预算可以加入：

- CI 构建检查
- Lighthouse CI
- Bundle Size 检查
- 发布前性能回归
- 线上版本对比

性能预算的意义是：

> 不要等页面已经非常卡，再开始抢救。

# 三十二、第三方脚本性能

第三方代码包括：

- 埋点
- 客服
- 广告
- 地图 SDK
- 视频播放器
- 登录 SDK
- 风控脚本

第三方脚本可能增加：

- 下载量
- JavaScript 执行
- 主线程长任务
- 网络连接
- 隐私和安全风险

官方性能指南也将第三方 JavaScript 视为常见性能风险来源。([web.dev](https://web.dev/articles/third-party-javascript?utm_source=chatgpt.com))

优化方法：

- 只在需要页面加载
- 延迟非关键脚本
- 评估替代库
- 限制重复 SDK
- 监控脚本执行时间
- 加载失败时允许业务降级
- 不让第三方脚本阻塞主流程

# 三十三、性能优化常见反效果

## 1. 预加载过多

所有资源都设置高优先级：

```text
所有人都是最高优先级
=
没有优先级
```

还会抢占 LCP 资源带宽。

## 2. 过度 useMemo

缓存成本比计算本身还高。

## 3. 过度 KeepAlive

页面快了，但内存不断增长。

## 4. 过度分包

请求瀑布增加。

## 5. 过度懒加载

首屏关键内容也被延迟。

## 6. 全量 Service Worker 缓存

用户长期看到旧版本。

## 7. 所有接口 Promise.all

服务端被瞬间打满。

## 8. 所有图片最高质量

清晰度提高很小，体积却增长几倍。

## 9. 为了跑分删除必要功能

跑分提高，但真实业务体验下降。

# 三十四、面试官连续追问

## 1. 你如何做性能优化？

> 我会先通过 RUM、Lighthouse、Performance 和 Network 明确瓶颈，再按照网络、资源、JavaScript 执行、框架渲染和用户交互逐层分析。优化后在相同环境复测，并观察线上 P75 和版本趋势。性能优化必须形成测量、归因、方案、复测和监控的闭环。

## 2. LCP 慢怎么排查？

> 先确认 LCP 元素是谁，再拆分 TTFB、资源加载延迟、资源下载和渲染延迟。服务器慢就优化缓存和后端；资源发现晚就把关键资源提前暴露在 HTML 中；下载慢就压缩和使用响应式图片；渲染慢则减少阻塞 JavaScript、CSS 和首屏串行请求。

## 3. INP 差怎么优化？

> 用 Performance 面板找到慢交互，区分输入等待、事件处理和呈现延迟。重点减少长任务、第三方脚本和回调同步计算，拆分任务，缩小状态更新范围，避免大型 DOM 布局；CPU 密集型任务可以移到 Worker。

## 4. 为什么包变小但页面没变快？

> 包体积只是下载因素，还要看压缩后传输大小、缓存、解析执行时间、请求瀑布、接口、图片和渲染。过度分包甚至可能让关键依赖串行加载，因此最终必须看 LCP、INP 和首屏业务指标。

## 5. 虚拟列表和分页有什么区别？

> 分页减少一次获取和管理的数据量，虚拟列表减少同时渲染的 DOM 数量。接口即使已经返回一万条数据，虚拟列表仍然有价值；使用虚拟列表后，也不代表接口无需分页。

## 6. 防抖能优化 INP 吗？

> 防抖可以减少搜索和校验等重复业务执行，但不能解决所有交互延迟。用户点击后需要立即反馈的操作不能一味防抖，真正问题可能是主线程长任务、过大渲染范围或同步布局。

## 7. 为什么不应该只看 Lighthouse？

> Lighthouse 是受控环境下的诊断工具，适合复现和定位；真实用户的数据包含不同设备、地区、网络和缓存状态。最终体验要看 RUM 和 P75，二者结合使用。

# 三十五、本章最容易漏掉的 20 个点

1. 性能优化前必须定义测量口径。
2. 当前 Core Web Vitals 是 LCP、INP、CLS。
3. 应重点观察真实用户 P75。
4. LCP 不只是图片下载时间。
5. 首屏 LCP 图不能随意懒加载。
6. INP 包含输入等待、处理和呈现。
7. Long Task 会阻塞用户输入。
8. 分片和 Worker 解决的问题不同。
9. CLS 不只是图片尺寸问题。
10. 骨架屏尺寸不匹配也会造成跳动。
11. JavaScript 体积还会影响解析和执行。
12. 包拆得越多不一定越快。
13. Tree Shaking 依赖可静态分析的模块结构。
14. Gzip、代码分割、缓存不是同一层优化。
15. 分页和虚拟列表可以同时使用。
16. Layout Thrashing 来自布局读写交替。
17. `transform` 也不是完全零成本。
18. `useMemo` 和 `React.memo` 不是默认必加。
19. SPA 路由切换需要补充自定义业务指标。
20. 优化数字必须说清平均值、P75、环境和数据口径。

# 三十六、本章五分钟必背答案

> 前端性能优化首先要明确指标和测量口径，然后通过实验室数据与真实用户数据定位问题。当前核心指标包括 LCP、INP 和 CLS，分别反映加载体验、交互响应和视觉稳定性。最终应重点观察真实用户第 75 百分位，而不是只看一次 Lighthouse 跑分。
>
> LCP 可以拆成服务器响应、资源发现、资源下载和元素渲染几个阶段。优化时应让首屏核心资源尽早被浏览器发现，使用合适尺寸和格式的图片，减少阻塞 JavaScript 和 CSS，并降低首屏串行依赖。
>
> INP 差通常与主线程长任务、事件处理过重、大规模状态更新和布局计算有关。可以减少不必要 JavaScript、拆分长任务、缩小组件更新范围、使用虚拟列表，并将 CPU 密集型计算交给 Web Worker。
>
> CLS 主要通过提前为图片、视频、广告和异步区域预留空间，保持骨架屏与真实内容尺寸一致，并优化字体加载来改善。
>
> 工程层面可以通过路由懒加载、动态 import、Tree Shaking、依赖分析、文本压缩和长期缓存减少首屏资源。但分包不是越细越好，压缩也不等于缓存，最终仍要通过真实指标验证。
>
> React 和 Vue 性能优化首先是状态位置、组件边界和 DOM 数量问题，之后才是 memo 化问题。对于超长列表要使用分页和虚拟列表，对于流式聊天应缓冲字符、批量更新、只解析变化消息并分层加载历史记录。
>
> 一个完整优化结果必须说明优化前后的同一指标、测试环境、统计口径、具体改动和副作用。性能优化的核心不是背优化清单，而是建立测量、归因、实施、复测和监控闭环。
