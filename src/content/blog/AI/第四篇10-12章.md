# 第 10 章：MCP 到底是什么

这是你简历里最容易被追问，同时也是最好快速掌握的概念之一。

先背一句标准定义：

> **MCP，Model Context Protocol，是一种用于 AI 应用与外部工具和数据源之间进行标准化连接与上下文交换的开放协议。**

你可以暂时把它理解成：

> **AI 世界里的 USB-C。**

------

# 一、没有 MCP 之前有什么问题？

假设我要开发一个 Agent。

它需要：

```text
GitHub
MySQL
文件系统
Notion
Slack
浏览器
```

以前可能：

```text
Claude → 自己写 GitHub Adapter
Claude → 自己写 MySQL Adapter
Claude → 自己写 Filesystem Adapter

另一个 Agent
      → 又写一套 GitHub Adapter
      → 又写一套 MySQL Adapter
```

出现：

```text
AI × Data Source
```

组合爆炸。

例如：

```text
5 个 AI Client
×
20 个外部系统
=
理论上大量单独适配
```

MCP 希望变成：

```text
               MCP Protocol

AI Host ──────────────────────────┐
                                 │
            ┌────────────────────┼───────────────┐
            ↓                    ↓               ↓
       GitHub MCP            MySQL MCP       Files MCP
         Server               Server          Server
```

这样不同 AI 应用都按照共同协议理解：

> “这个 Server 提供了哪些能力？”

这就是 MCP 的价值。

------

# 二、最核心的三层角色

面试必须会：

```text
Host
Client
Server
```

官方架构中，Host 是 AI 应用本身，Host 管理一个或多个 MCP Client，而通常每个 Client 维护到一个 MCP Server 的连接。Server 可以在本地，也可以是远程服务。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

你可以这样理解：

```text
┌─────────────────────────────┐
│           MCP Host          │
│                             │
│ Claude Code / IDE / Agent   │
│                             │
│  ┌────────┐   ┌────────┐    │
│  │Client A│   │Client B│    │
│  └───┬────┘   └───┬────┘    │
└──────┼─────────────┼─────────┘
       ↓             ↓
 GitHub MCP       DB MCP
   Server          Server
```

------

## Host

负责整个 Agent。

例如：

```text
LLM
上下文
用户权限
多个 MCP Server
Agent Loop
```

都由 Host 协调。

一句话：

> **Host 是总指挥。**

------

## Client

Host 内负责和某一个 Server 通信。

一句：

> **Client 是连接器。**

------

## Server

对外提供具体能力。

例如：

```text
GitHub MCP Server

可能提供：
搜索仓库
读取文件
创建Issue
读取PR
```

一句：

> **Server 是能力提供方。**

------

# 三、MCP Server 到底提供什么？

这一块必须重点背。

核心三个：

```text
Tools
Resources
Prompts
```

官方 MCP 文档把它们定义为 Server 可以提供的核心 primitives。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

------

## 1. Tools

可以执行的动作。

例如：

```text
search_repository()
read_file()
create_issue()
query_database()
```

所以：

> **Tool = 行动能力。**

------

## 2. Resources

可以读取的上下文数据。

例如：

```text
文件内容
数据库 Schema
Git History
项目文档
API 返回数据
```

所以：

> **Resource = 数据 / 上下文。**

官方文档指出 Resource 可以代表文件、数据库记录、API 数据等，并由 Host 决定如何纳入模型 Context。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-03-26/server/resources?utm_source=chatgpt.com))

------

## 3. Prompts

可复用的提示模板。

例如：

```text
/code-review
/analyze-pr
/database-debug
```

所以：

> **Prompt = 可复用交互模板。**

------

# 四、三个东西怎么区分？

背这张：

| MCP Primitive | 本质       | 例子             |
| ------------- | ---------- | ---------------- |
| Tool          | 做事情     | 创建 Issue       |
| Resource      | 给资料     | 读取项目文件     |
| Prompt        | 给方法模板 | Code Review 模板 |

可以记：

```text
Tools
= 做

Resources
= 看

Prompts
= 怎么做
```

虽然是简化记忆，但非常好用。

------

# 五、Tool Calling 和 MCP 到底有什么区别？

这是 MCP 第一高频面试题。

你一定不要回答：

> 差不多，都是调用工具。

不是。

## Tool Calling

解决：

> **模型怎么决定调用什么工具，并产生参数。**

例如：

```text
LLM

↓

{
  "tool": "search_repository",
  "arguments": {
    "query": "RAG"
  }
}
```

------

## MCP

解决：

> **这些 Tool / Resource 如何以标准协议被 AI 应用发现、描述和访问。**

例如：

```text
MCP Client

↓

tools/list

↓

MCP Server

↓

[
 search_repository,
 read_file,
 create_issue
]
```

------

所以核心关系：

```text
Tool Calling
=
“我要调用哪个能力？”

MCP
=
“这些能力通过什么标准方式接进来？”
```

非常重要。

你可以背：

> **Tool Calling 是模型层面的工具选择机制，MCP 是应用与外部工具、数据源之间的标准化连接协议。两者不是竞争关系，MCP 提供的 Tool 最终仍然可以由模型通过 Tool Calling 进行选择。**

这基本就是标准答案。

------

# 六、API 和 MCP 又有什么区别？

面试官可能追问：

> API 已经存在这么多年了，为什么还需要 MCP？

这是好问题。

API：

```text
GET /repos
POST /issues
GET /users
```

主要服务：

> 软件和软件之间调用。

但是不同 API：

```text
认证方式不同
Schema不同
文档不同
发现方式不同
错误结构不同
调用方式不同
```

Agent 需要额外适配。

MCP 在 API 上方增加一个：

> 面向 AI Client 的标准协议层。

可以理解：

```text
        Agent
          ↓
        MCP
          ↓
      MCP Server
          ↓
   GitHub API / DB / FS
```

所以：

> **MCP 通常不是替代底层 API，而是把底层能力包装成 AI 应用容易统一发现和调用的标准接口。**

这一句话非常关键。

------

# 七、MCP 是怎么发现 Tool 的？

MCP 不是要求：

> 你提前把所有工具写进一个巨大 Prompt。

Client 可以请求：

```text
tools/list
```

Server 返回：

```text
name
description
input schema
...
```

然后：

```text
tools/call
```

调用相应工具。

这种动态发现是 MCP 很重要的思想之一。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

和你上一章 Tool Schema 就直接接起来了。

------

# 八、MCP 底层传什么？

你不用深入协议源码。

只需要记：

> **MCP 的消息层基于 JSON-RPC。**

官方当前文档也是这么描述的。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

大概：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/list",
  "id": 1
}
```

不用背 JSON。

知道：

```text
MCP
不是HTTP API的一个固定URL规范

而是一套定义：
消息
能力
发现
调用
通信
```

即可。

------

# 九、MCP 怎么通信？

当前面试重点掌握两个：

```text
stdio
Streamable HTTP
```

官方文档把它们列为标准传输方式。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports?utm_source=chatgpt.com))

------

## stdio

本地进程：

```text
Agent Host

启动：

node github-server.js

        ↓

stdin / stdout

        ↓

MCP Server
```

特别适合：

```text
本地文件系统
开发工具
CLI
本地数据库
```

------

## Streamable HTTP

远程：

```text
Agent
 ↓
HTTP
 ↓
Remote MCP Server
```

适合：

```text
SaaS
云服务
企业系统
```

你记：

```text
Local → stdio

Remote → Streamable HTTP
```

只是常见模式，不是绝对规则。

------

# 十、为什么 MCP 不是“Agent”？

这个一定要知道。

```text
MCP
≠
Agent
```

MCP 本身并不会：

```text
思考
规划
决定下一步
循环执行任务
```

它只是：

> Connection / Context Protocol。

官方文档也明确强调，MCP 聚焦于协议和上下文交换，并不规定 AI 应用如何使用 LLM 或如何管理上下文。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

所以：

```text
Agent
    ↓
使用
    ↓
MCP
    ↓
外部能力
```

------

# 十一、为什么 MCP 也需要权限控制？

假设：

```text
GitHub MCP Server
```

暴露：

```text
read_repo
delete_repo
force_push
```

Agent 发生 Prompt Injection：

> 删除仓库。

风险就非常大。

所以：

```text
MCP标准化连接
≠
MCP自动保证业务安全
```

仍然需要：

```text
OAuth
权限 Scope
最小权限
用户确认
Tool Allowlist
审计日志
```

官方 MCP 架构也把权限、用户授权和安全边界放在 Host 的责任中；HTTP MCP 还定义了授权机制。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-06-18/architecture?utm_source=chatgpt.com))

面试加分：

> **Protocol interoperability 和 Agent safety 是两个问题，不能因为用了 MCP 就认为 Tool 安全已经解决。**

很好。

# 十二、关于 MCP 的最新变化，哪些不用背？

截至 **2026 年 8 月**，MCP 仍在快速演化。7 月发布的新规范候选版本继续推进 stateless core、Extensions、Tasks 和授权强化，同时 Roots、Sampling、Logging 等旧能力已进入弃用方向。([Model Context Protocol](https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging?utm_source=chatgpt.com))

你一天速成完全**不要把精力浪费在这些边缘版本细节上**。

面试牢牢记：

```text
MCP

Host
Client
Server

Tools
Resources
Prompts

JSON-RPC

stdio
Streamable HTTP
```

足够。

------

# 十三、MCP 面试标准答案

面试官：

> 什么是 MCP？

你回答：

> MCP 是 Model Context Protocol，我把它理解成 AI 应用连接外部能力的一层标准协议。过去每个 Agent 都需要分别适配 GitHub、数据库、文件系统等不同接口，而 MCP 通过 Host、Client、Server 架构，让 Server 可以用统一协议暴露 Tools、Resources 和 Prompts，AI Host 可以进行能力发现和调用。
>
> MCP 本身不是 Agent，也不负责模型如何推理。Tool Calling 解决的是模型“决定调用哪个工具并生成参数”，MCP 解决的是这些工具和数据源“如何标准化接入 AI 应用”。底层 MCP 使用 JSON-RPC，常见 Transport 有本地 stdio 和远程 Streamable HTTP。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

建议背。

# 第 11 章：Memory、Skill、Harness

这三个词是你简历 AI 一栏最后三个必须撑住的概念。

而且一定要分清：

```text
Memory ≠ RAG

Skill ≠ Tool

Harness ≠ Agent
```

------

# 一、Memory 到底是什么？

先背：

> **Agent Memory 是让系统在当前步骤之外保存和重新利用过去信息、状态、经验或用户偏好的机制。**

为什么要 Memory？

因为模型本身每次 API 调用：

> 不天然拥有永久记忆。

如果你第二天开新请求：

```text
“继续昨天的工作”
```

而应用没有保存任何东西：

> 模型不知道“昨天”发生了什么。

------

# 二、Context 和 Memory 区别

这个非常重要。

```text
Memory
= 仓库

Context
= 当前桌面
```

Memory 里可能有：

```text
1000条历史
```

但模型 Context Window 不能全部放。

所以：

```text
Memory
 ↓
Retrieve / Select
 ↓
Relevant Memory
 ↓
Context
 ↓
LLM
```

这和 RAG 非常像。

实际上：

> **Memory Retrieval 本质上经常也会使用检索思想。**

------

# 三、Short-term Memory

简单理解：

> 当前任务过程中的状态。

例如 Agent：

```text
Step1：找到了5篇文章

Step2：已经读取3篇

Step3：还剩2篇
```

这些状态必须保留。

否则 Agent 每一步都：

> “我刚才干嘛了？”

------

# 四、Long-term Memory

跨 Session 保存。

例如：

```text
用户喜欢中文回答
项目技术栈 Astro + React
博客文章路径规则
之前已经分析过哪些文章
```

以后再检索回来。

------

# 五、你只要记 3 类 Memory

不用学几十种术语。

### Conversation Memory

历史聊天：

```text
User
Assistant
User
Assistant
```

------

### Semantic Memory

事实：

```text
用户项目使用Astro
博客部署在Vercel
```

------

### Episodic Memory

过去发生过的任务经历：

```text
上一次修复AI Gateway时
DeepSeek曾返回429
最后通过限流处理
```

你把这三个概念懂了即可。

------

# 六、Memory 和 RAG 有什么区别？

高频。

RAG：

```text
通常检索外部知识
```

例如：

```text
博客
PDF
企业Wiki
```

Memory：

```text
通常检索过去交互和Agent自身状态
```

所以：

```text
RAG：
“世界知道什么？”

Memory：
“这个Agent / 用户之前发生过什么？”
```

但实现层：

```text
Chunk
Embedding
Vector Search
Metadata
```

可能高度相似。

------

# 七、Memory 不是越多越好

如果 Agent 什么都记：

```text
用户每句话
每个Tool Result
所有无意义状态
```

会产生：

```text
Memory Noise
Storage增长
隐私风险
错误记忆
Context污染
```

所以好的 Memory 体系需要：

```text
Write Policy
Retrieve Policy
Forget / Update Policy
```

也就是：

> 什么值得记，什么时候取出来，什么时候删除或更新。

这句话很重要。

------

# 八、Skill 到底是什么？

这里一定要准确。

**Skill 不是所有 Agent 框架统一规定的基础概念。**

但当前 Agent Skills 体系里，可以把 Skill 理解成：

> **针对某类任务打包好的可复用专业知识、工作流程、指令和可选脚本/资源，让通用 Agent 在需要时加载并按照既定方法完成任务。**

目前 Agent Skills 规范中，一个 Skill 至少包含：

```text
skill-name/
└── SKILL.md
```

还可以有：

```text
scripts/
references/
assets/
```

`SKILL.md` 包含 Metadata 和具体 Instructions。([Agent Skills](https://agentskills.io/specification?utm_source=chatgpt.com))

Anthropic 当前官方文档也采用这种基于文件系统、按需加载的 Skill 模型。([Claude Platform](https://platform.claude.com/docs/zh-CN/agents-and-tools/agent-skills/overview?utm_source=chatgpt.com))

------

# 九、给你一个非常直观的 Skill

比如：

```text
frontend-code-review/
│
├─ SKILL.md
├─ references/
│  └─ review-rules.md
│
└─ scripts/
   └─ analyze-bundle.js
```

SKILL.md：

```markdown
---
name: frontend-code-review
description: 用于前端项目代码审查和性能排查
---

# Workflow

1. 先检查项目结构
2. 检查 React/Vue 状态设计
3. 检查重复渲染
4. 检查包体积
5. 检查 XSS
6. 输出严重程度
```

Agent 遇到：

> 帮我 review 这个前端项目。

就可以加载这个 Skill。

------

# 十、Skill 和 Prompt 有什么区别？

Prompt：

```text
这一次告诉AI：
帮我按照以下规则检查代码……
```

Skill：

```text
把这套规则长期封装起来
```

所以：

> **Prompt 更像一次性指导，Skill 更像可复用的任务操作手册。**

------

# 十一、Skill 和 Tool 又有什么区别？

这个必须背。

例如：

### Tool

```text
read_file()
```

它解决：

> **能做什么。**

------

### Skill

```text
code-review skill
```

告诉 Agent：

```text
先读哪些文件
检查什么
怎么判断
最后怎么输出
```

它解决：

> **应该怎么做。**

所以一句：

```text
Tool
= Capability

Skill
= Procedure / Expertise
```

翻中文：

> **Tool 是能力，Skill 是方法。**

非常好背。

------

# 十二、Skill 和 MCP 又是什么关系？

MCP：

> 标准化把 Tool / Resource 接给 Agent。

Skill：

> 告诉 Agent 如何组合这些能力完成某类任务。

例如：

```text
Frontend Review Skill
        ↓
要求：
读取package.json
读取源码
运行测试
检查Git Diff
        ↓
实际能力来自：
Filesystem MCP
GitHub MCP
Terminal Tool
```

所以：

```text
MCP
= 接工具

Skill
= 用工具的方法
```

------

# 十三、Skill 为什么经常使用“渐进加载”？

这是非常好的 AI 工程思想。

假设有：

```text
100 个 Skill
```

如果启动时：

```text
100 个 SKILL.md
全部塞入Context
```

Context 爆炸。

因此当前 Agent Skills 思路一般是：

```text
启动时：

Name
Description

↓

判断相关

↓

再加载完整 SKILL.md

↓

需要时再读取references / scripts
```

Agent Skills 官方规范和 Anthropic 文档都强调这种按需 / 渐进式加载。([Agent Skills](https://agentskills.io/specification?utm_source=chatgpt.com))

你马上应该想到：

> **Context Engineering。**

这和我们第二章完全接上了。

------

# 十四、Harness 到底是什么？

这个概念经常被说得特别玄。

先说明：

> **Agent Harness 并不是像 MCP 那样有唯一统一标准协议，它更多是一个工程概念。**

你可以理解：

> **Harness 是包在 LLM 外面、负责让 Agent 真正稳定执行任务的一整套运行时和基础设施。**

核心图：


# 三、面试官：介绍一下你博客的 AI 功能

# 八、面试官：RAG 和 Agent 最大区别是什么？

# 九、面试官：Tool Calling 和 MCP 最大区别？

# 最后：第四批每天背诵版

## 第一段：MCP

> MCP 是 Model Context Protocol，是 AI 应用连接外部工具和数据源的一套标准协议。核心架构包括 Host、Client 和 Server，Server 可以暴露 Tools、Resources 和 Prompts。MCP 的消息层基于 JSON-RPC，常见传输包括本地 stdio 和远程 Streamable HTTP。
>
> Tool Calling 解决的是模型如何选择工具和生成参数，MCP 解决的是工具和数据源如何标准化接入 AI 应用。MCP 本身不是 Agent，它只负责能力和上下文的连接。([Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture?utm_source=chatgpt.com))

------

## 第二段：Memory / Skill / Harness

> Memory 用来保存和复用当前 Context 之外的信息，可以包括 Conversation、Semantic 和 Episodic Memory。Memory 是长期仓库，Context 是当前工作区，因此通常需要从 Memory 中检索真正相关的信息再送进 Context。
>
> Tool 表示 Agent 能做什么，而 Skill 表示一类任务应该怎么做。当前 Agent Skills 通常通过 SKILL.md 封装 Metadata、Instructions 和可选 Scripts、References，并按需加载以减少 Context 消耗。([Agent Skills](https://agentskills.io/specification?utm_source=chatgpt.com))
>
> Harness 是 Agent 外围的运行时基础设施，主要处理 Context、Tool Execution、Agent Loop、State、Permission、Sandbox、Retry、Timeout 和 Observability。

------

## 第三段：Agent 总结

> Agent 是以 LLM 为核心决策能力，根据 Goal 和当前 Observation 动态决定下一步行动的系统。它通过 Tool Calling 与外部环境交互，通过 RAG 获取知识，通过 Memory 保存过去，通过 Skill 获得专业工作方法，通过 MCP 标准化连接外部能力，而 Harness 负责让整个过程安全稳定运行。
>
> 能用确定性 Workflow 解决的问题不应该为了 Agent 而 Agent，真正适合 Agent 的任务通常是目标明确但执行路径需要根据环境动态变化的复杂任务。
