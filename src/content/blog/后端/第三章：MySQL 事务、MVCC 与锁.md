# 一、为什么需要事务？

假设用户购买一瓶酒，需要完成两步：

1. 订单表新增订单。
2. 商品库存减一。

如果订单创建成功，但库存扣减失败，就会出现：

> 用户有订单，但库存没有减少。

如果库存扣减成功，但订单创建失败，则会出现：

> 库存少了一瓶，却没人买到。

我们希望这两个操作：

> 要么全部成功，要么全部失败。

这就是事务。

## 事务的基本写法

```sql
-- 开启一个事务，后面的操作暂时不会立即永久生效
START TRANSACTION;

-- 创建一条新订单记录
INSERT INTO orders (
  order_no,       -- 订单编号
  user_id,        -- 用户 ID
  product_id,     -- 商品 ID
  amount,         -- 订单金额
  status          -- 订单状态
)
VALUES (
  'ORDER20260730001', -- 新订单编号
  1001,               -- 当前下单用户 ID
  2001,               -- 当前购买商品 ID
  999.00,             -- 商品价格
  0                   -- 0 表示待支付
);

-- 将商品库存减一
UPDATE products
SET stock = stock - 1
WHERE id = 2001;

-- 前面的操作全部成功，正式提交事务
COMMIT;
```

如果中途发现错误：

```sql
-- 回滚当前事务，撤销本次事务内已经执行的修改
ROLLBACK;
```

你可以把事务想象成游戏存档：

```text
开始事务：创建临时存档
执行 SQL：在临时存档中修改
COMMIT：确认保存
ROLLBACK：读档重来
```

## 面试标准答案

> 事务是数据库执行操作的基本单元，一组操作要么全部成功，要么全部失败。例如创建订单和扣减库存必须保持一致，任何一步失败都应该回滚，避免出现订单与库存数据不一致。

------

# 二、事务的 ACID

事务有四个核心特性：

```text
A：Atomicity，原子性
C：Consistency，一致性
I：Isolation，隔离性
D：Durability，持久性
```

你可以记成：

> **原、一、隔、持。**

------

## 1. 原子性：要么全做，要么全不做

创建订单和减少库存是一组操作。

不能出现：

- 订单创建了，库存没减少；
- 库存减少了，订单没创建。

这叫原子性。

### 背诵答案

> 原子性表示一个事务中的操作是不可分割的整体，要么全部成功，要么全部失败回滚。

------

## 2. 一致性：执行前后，数据规则不能被破坏

假设数据库规定：

```text
库存不能小于 0
订单金额不能为负数
订单必须属于某个用户
```

执行事务以后，这些规则仍然要成立。

一致性是事务的最终目标，其他三个特性共同帮助实现一致性。

### 背诵答案

> 一致性表示事务执行前后，数据库都必须处于合法状态，不能破坏库存、金额、外键等业务约束。

------

## 3. 隔离性：同时操作时，尽量互不干扰

两个人同时购买最后一瓶酒。

数据库不能让两个事务随意看到对方还没提交的数据，否则就容易混乱。

### 背诵答案

> 隔离性表示多个事务并发执行时，一个事务的中间状态不应该随意影响其他事务。

------

## 4. 持久性：提交成功后不能轻易丢失

一旦数据库返回提交成功，即使服务器突然断电，数据库恢复后也应该尽量保留已经提交的数据。

### 背诵答案

> 持久性表示事务一旦成功提交，对数据库的修改就应该被永久保存。

------

# 三、三个并发问题

假设你正在查询万福鉴酒订单，另一个管理员正在修改订单。

并发执行时，可能出现三个经典问题。

------

# 四、脏读：读到了别人没提交的数据

事务 A 把订单金额从 999 元修改为 1 元，但还没有提交。

事务 B 此时读取到了 1 元。

随后事务 A 发现操作错误，执行回滚，金额重新变成 999 元。

事务 B 刚才看到的 1 元，从来没有真正生效。

这就是脏读。

```text
事务 A：把金额改成 1 元，但没提交
事务 B：读到了 1 元
事务 A：回滚，金额恢复成 999 元
事务 B：刚才读到的是“脏数据”
```

## 背诵答案

> 脏读是指一个事务读取到了另一个事务尚未提交的数据。如果另一个事务随后回滚，那么读取到的数据就是无效的脏数据。

------

# 五、不可重复读：同一行，两次读取结果不同

事务 A 第一次查询订单状态：

```text
待支付
```

事务 B 将它修改为：

```text
已支付
```

并且提交。

事务 A 再次查询同一条订单，看到：

```text
已支付
```

同一个事务中，两次读取同一行，结果不同，这叫不可重复读。

```text
事务 A：第一次读取，状态是“待支付”
事务 B：修改为“已支付”并提交
事务 A：第二次读取，状态变成“已支付”
```

## 背诵答案

> 不可重复读是指在同一个事务中，对同一条记录进行多次读取，前后结果不同，通常是因为其他事务修改并提交了这条记录。

------

# 六、幻读：同样的条件，两次查询行数不同

事务 A 查询所有待支付订单，查到 10 条。

事务 B 新增一条待支付订单并提交。

事务 A 再查询一次，结果变成 11 条。

就好像凭空多出了一条“幻影数据”。

这叫幻读。

```text
事务 A：查询待支付订单，共 10 条
事务 B：新增一条待支付订单并提交
事务 A：再次查询，共 11 条
```

## 背诵答案

> 幻读是指在同一个事务中，使用相同条件进行范围查询，前后返回的记录数量不同，通常是因为其他事务插入或删除了符合条件的数据。

------

# 七、不可重复读和幻读的区别

这是高频追问。

## 不可重复读

关注：

> 同一条数据被修改了。

例如：

```text
订单 1001：
待支付 → 已支付
```

## 幻读

关注：

> 查询结果中增加或减少了数据行。

例如：

```text
待支付订单：
10 条 → 11 条
```

一句话记忆：

> **不可重复读是“这一行变了”，幻读是“行数变了”。**

------

# 八、四种事务隔离级别

不同隔离级别，就是数据库在下面两件事之间做选择：

```text
安全性
性能与并发能力
```

隔离越严格，数据越安全，但并发处理成本通常也越高。

| 隔离级别         | 中文     | 脏读 | 不可重复读 | 幻读           |
| ---------------- | -------- | ---- | ---------- | -------------- |
| Read Uncommitted | 读未提交 | 可能 | 可能       | 可能           |
| Read Committed   | 读已提交 | 避免 | 可能       | 可能           |
| Repeatable Read  | 可重复读 | 避免 | 避免       | 通常可较好处理 |
| Serializable     | 串行化   | 避免 | 避免       | 避免           |

记忆方式：

```text
读未提交：别人没提交，我也敢看
读已提交：别人提交以后，我才看
可重复读：事务期间，我尽量看到同一个版本
串行化：一个一个来，别抢
```

------

## 1. 读未提交

隔离级别最低。

一个事务可以读取另一个事务尚未提交的数据，因此可能出现脏读。

可以想象成：

> 同学答题还没写完，你已经把草稿偷看了。

实际业务中较少使用。

------

## 2. 读已提交

只能读取其他事务已经提交的数据，因此避免了脏读。

但是在同一个事务中，别人提交修改后，你再次查询可能看到新值，所以仍可能发生不可重复读。

可以想象成：

> 别人交卷以后，你才可以看，但他每次交新版本，你看到的内容也会变化。

------

## 3. 可重复读

同一个事务中，多次普通读取通常看到一致的数据版本。

MySQL InnoDB 常用的默认隔离级别就是可重复读。

可以想象成：

> 事务开始时，数据库给你拍了一张照片。后面别人怎么修改，你普通查询时仍然主要看这张照片。

这是理解 MVCC 的关键。

------

## 4. 串行化

隔离级别最高。

多个事务像排队一样，一个一个执行。

安全性高，但并发能力相对较低。

可以想象成最后一瓶酒只允许：

```text
用户 A 完全操作结束
        ↓
用户 B 才能开始操作
```

------

# 九、如何查看和修改隔离级别？

下面只要求你看懂，不需要死记命令。

```sql
-- 查看当前会话使用的事务隔离级别
SELECT @@transaction_isolation;
-- 将当前会话的隔离级别设置为读已提交
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 将当前会话的隔离级别设置为可重复读
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

面试中一般不会让前端手写这些命令，重点是理解四个级别解决了什么问题。

------

# 十、MVCC：数据库的“平行时间线”

现在进入本章最重要、也最容易显得你有水平的知识点。

MVCC 全称：

> Multi-Version Concurrency Control，多版本并发控制。

不要被英文吓到。

它的核心思想是：

> 同一条数据可以保留多个历史版本，不同事务根据规则看到适合自己的版本。

------

## 一个故事

订单最开始是：

```text
版本 1：待支付
```

后来管理员修改为：

```text
版本 2：已支付
```

再后来退款：

```text
版本 3：已退款
```

数据库不会简单地只考虑最新值，而是会保留历史修改线索。

不同事务可能看到：

```text
事务 A：看到版本 1
事务 B：看到版本 2
事务 C：看到版本 3
```

这就像三个人站在不同时间点看同一个订单。

------

# 十一、MVCC 为什么有用？

如果完全不用 MVCC，为了保证读取稳定，查询数据时可能需要大量加锁。

例如：

```text
事务 A 正在读取订单
事务 B 想修改订单
事务 B 只能一直等待
```

并发能力就会变差。

有了 MVCC：

```text
事务 A 读取旧版本
事务 B 修改新版本
两者很多情况下可以同时进行
```

也就是：

> **读写之间尽量互不阻塞。**

------

# 十二、MVCC 只需要记住三个东西

一天速成阶段，你只背这三个：

## 1. Undo Log：保存历史版本

当数据被修改时，MySQL 会记录修改前的信息，用于：

- 事务回滚；
- 构建历史版本；
- 支持 MVCC。

你可以把 Undo Log 理解成：

> 数据库的“撤销记录”和“历史存档”。

------

## 2. 事务 ID：标记是谁修改的

每个修改数据的事务都有自己的事务标识。

数据库可以据此判断：

- 这个版本是谁创建的；
- 创建它的事务是否已经提交；
- 当前事务能不能看到它。

------

## 3. Read View：可见性名单

Read View 可以理解成事务拍照时生成的一张名单。

它会帮助数据库判断：

> 哪些事务的数据版本，我可以看；哪些版本现在还不能看。

------

## MVCC 标准答案

> MVCC 是多版本并发控制。InnoDB 通过事务 ID、Undo Log 保存的历史版本以及 Read View 可见性判断，让不同事务读取适合自己的数据版本，从而在保证隔离性的同时，减少读写之间的阻塞，提高并发性能。

这段值得完整背下来。

------

# 十三、快照读和当前读

这个知识点很适合面试追问。

## 快照读

普通查询通常属于快照读。

```sql
-- 普通查询通常根据 MVCC 读取当前事务可见的数据版本
SELECT id, order_no, status
FROM orders
WHERE id = 1001;
```

它读到的不一定是此刻物理意义上的最新版本，而是：

> 当前事务按照隔离规则应该看到的版本。

------

## 当前读

加锁查询、修改和删除通常需要读取最新数据。

```sql
-- 查询订单的最新数据，并对该记录加排他锁
SELECT id, order_no, status
FROM orders
WHERE id = 1001
FOR UPDATE;
```

常见当前读包括：

```text
SELECT ... FOR UPDATE
UPDATE
DELETE
INSERT
```

一句话记忆：

> **普通 SELECT 常是快照读，加锁查询和修改操作通常是当前读。**

------

# 十四、什么是锁？

锁的核心目的：

> 防止多个事务同时修改同一份关键数据，产生冲突。

你可以想象厕所门锁。

没有锁时：

```text
用户 A 正在使用
用户 B 直接冲进来
现场失控
```

有锁时：

```text
用户 A 上锁
用户 B 等待
用户 A 离开并解锁
用户 B 进入
```

数据库也是类似逻辑。

------

# 十五、共享锁和排他锁

## 共享锁

又叫读锁。

多个事务可以共同读取，但会限制其他事务进行冲突修改。

```sql
-- 读取指定订单，并为它添加共享锁
SELECT id, order_no, status
FROM orders
WHERE id = 1001
FOR SHARE;
```

可以理解为：

> 大家可以一起看，但暂时不能随便改。

------

## 排他锁

又叫写锁。

某个事务获得排他锁后，其他事务不能再对同一数据进行冲突修改。

```sql
-- 读取指定订单的最新数据，并添加排他锁
SELECT id, order_no, status
FROM orders
WHERE id = 1001
FOR UPDATE;
```

可以理解为：

> 我正在修改，其他人先等着。

------

# 十六、行锁和表锁

## 行锁

只锁住某几行数据。

例如只锁商品 2001：

```sql
-- 查询商品 2001 的库存，并锁住这一行数据
SELECT id, name, stock
FROM products
WHERE id = 2001
FOR UPDATE;
```

其他人仍然可以操作商品 2002、2003。

优点：

- 锁范围小；
- 并发能力较好。

------

## 表锁

锁住整张表。

其他事务对整张表的操作都可能受到影响。

优点是实现简单，但并发能力相对较差。

面试时记住：

> InnoDB 更擅长使用行级锁，但是否真正锁到少量行，与查询条件和索引情况有关。

例如查询条件没有合适索引，数据库可能需要扫描大量记录，锁影响范围也可能增大。

所以：

> **索引不仅影响查询性能，也可能影响锁的范围。**

这句话说出来很加分。

------

# 十七、悲观锁：我觉得一定有人和我抢

悲观锁的思想是：

> 我认为并发冲突很可能发生，所以先把数据锁住，再进行修改。

现在只剩最后一瓶酒。

可以这样处理：

```sql
-- 开启事务，保证查询库存和扣减库存属于同一个操作单元
START TRANSACTION;

-- 查询商品最新库存，并使用排他锁锁住该商品记录
SELECT id, name, stock
FROM products
WHERE id = 2001
FOR UPDATE;

-- 确认库存大于 0 后，将库存减一
UPDATE products
SET stock = stock - 1
WHERE id = 2001
  AND stock > 0;

-- 所有操作成功后提交事务，同时释放锁
COMMIT;
```

执行过程：

```text
用户 A 先获得商品锁
用户 B 只能等待
用户 A 扣减库存并提交
用户 B 获得锁后发现库存已经是 0
用户 B 下单失败
```

这样可以避免两个人同时买到最后一瓶。

------

# 十八、乐观锁：我先改，冲突了再说

乐观锁认为：

> 大多数时候不会冲突，所以不提前锁住数据；提交修改时，再检查数据有没有被别人改过。

通常会增加一个版本号：

```sql
-- 创建商品表，并使用 version 字段记录数据版本
CREATE TABLE products (
  id BIGINT PRIMARY KEY,          -- 商品主键 ID
  name VARCHAR(100) NOT NULL,     -- 商品名称
  stock INT NOT NULL,             -- 当前库存数量
  version INT NOT NULL DEFAULT 0  -- 数据版本号，每次修改后加一
);
```

假设前端或后端查询到：

```text
商品 ID：2001
库存：1
版本号：5
```

更新时：

```sql
-- 只有库存仍大于 0，并且版本号仍然是 5 时，才允许扣减库存
UPDATE products
SET stock = stock - 1,  -- 库存减一
    version = version + 1  -- 版本号加一，表示数据已被修改
WHERE id = 2001  -- 只修改目标商品
  AND stock > 0  -- 确保库存充足
  AND version = 5;  -- 确保数据没有被其他事务修改
```

如果用户 A 已经成功修改，版本号会变成 6。

用户 B 仍然拿着旧版本号 5 修改时：

```text
受影响行数 = 0
```

表示修改失败，需要：

- 重新读取数据；
- 提示库存不足；
- 或在合理范围内重试。

------

# 十九、乐观锁和悲观锁怎么选？

## 悲观锁

适合：

- 并发冲突概率高；
- 操作时间短；
- 强调修改安全；
- 库存扣减、抢购等场景。

缺点：

- 其他事务可能等待；
- 持锁时间过长会影响性能；
- 使用不当可能死锁。

## 乐观锁

适合：

- 读多写少；
- 冲突概率相对低；
- 希望减少数据库锁等待；
- 表单编辑、状态更新等场景。

缺点：

- 冲突后要重试或提示失败；
- 高冲突场景可能频繁失败。

## 面试标准答案

> 悲观锁认为并发冲突很可能发生，因此先通过 `FOR UPDATE` 等方式锁住数据，再执行修改；乐观锁通常通过 version 版本号或时间戳，在更新时判断数据是否被其他事务修改。冲突频繁且要求强一致的场景可以考虑悲观锁，读多写少、冲突较少的场景可以考虑乐观锁。

------

# 二十、最容易写错的库存扣减

下面这种写法有风险：

```sql
-- 先单独查询商品库存
SELECT stock
FROM products
WHERE id = 2001;
```

业务代码判断：

```text
库存是 1，可以购买。
```

然后再执行：

```sql
-- 将商品库存减一，但没有进行版本或并发条件判断
UPDATE products
SET stock = stock - 1
WHERE id = 2001;
```

问题是两个人可能同时查到：

```text
库存都是 1
```

随后两个人都执行减一。

最终可能出现：

```text
库存 = -1
```

更稳妥的方式是直接带条件更新：

```sql
-- 只有库存大于 0 时才进行扣减，避免库存被直接减成负数
UPDATE products
SET stock = stock - 1
WHERE id = 2001
  AND stock > 0;
```

然后检查受影响行数：

```text
受影响行数为 1：扣减成功
受影响行数为 0：库存不足或数据不存在
```

这条非常实用。

# 二十一、什么是死锁？

事务 A：

```text
先锁住商品 1
再等待商品 2
```

事务 B：

```text
先锁住商品 2
再等待商品 1
```

两个人互相等待：

```text
事务 A：你先释放商品 2
事务 B：你先释放商品 1
事务 A：你先
事务 B：你先
……
```

这就是死锁。

------

## 如何减少死锁？

重点背四点：

1. 多个事务按照相同顺序操作数据。
2. 尽量缩短事务执行时间。
3. 不要在事务中执行耗时的网络请求。
4. 给查询条件建立合适索引，减少锁定范围。

错误做法：

```text
开启数据库事务
    ↓
锁住订单
    ↓
请求第三方支付接口，等待五秒
    ↓
更新数据库
```

这五秒期间锁一直不释放，其他请求都可能等待。

更合理的思路是：

> 数据库事务中只做必要、快速的数据库操作，外部网络调用不要长时间占着数据库锁。

------

# 二十二、事务中不要做什么？

不要在事务里长时间执行：

- 调用 AI 大模型；
- 上传 OSS 文件；
- 调用支付平台；
- 发送短信；
- 请求地图接口；
- 执行复杂网络请求。

因为这些操作可能很慢，导致事务迟迟不提交，锁也无法及时释放。

以你的 TripStar AI 为例，不能这样设计：

```text
开启数据库事务
    ↓
等待大模型生成几十秒
    ↓
保存旅行计划
    ↓
提交事务
```

更合理的方式：

```text
先创建“生成中”任务并提交
    ↓
异步调用大模型
    ↓
生成完成后开启一个短事务
    ↓
保存正式行程并更新任务状态
```

# 二十三、结合你的项目如何回答

## 万福鉴酒：订单状态更新

面试官可能问：

> 用户端和鉴定师端同时修改订单状态，如何防止状态被错误覆盖？

你可以回答：

> 如果让我设计，我会在更新订单状态时增加旧状态条件或 version 版本号。例如只有当前状态仍然是“待接单”时，才允许更新为“进行中”。如果受影响行数为 0，说明状态已经被其他请求修改，前端应重新拉取最新状态，而不是直接覆盖。

对应 SQL：

```sql
-- 只有订单当前仍然处于待接单状态时，才更新为进行中
UPDATE orders
SET status = 20,          -- 将订单状态修改为进行中
    updated_at = NOW()    -- 更新最后修改时间
WHERE id = 1001           -- 指定需要修改的订单
  AND status = 10;        -- 确保订单当前仍然是待接单
```

这样可以避免：

```text
订单已经退款
却又被旧请求修改成进行中
```

## 生猪健康系统：药品库存

面试官可能问：

> 两个养殖户同时购买最后一份药品怎么办？

你可以回答：

> 可以使用带库存条件的原子更新，确保只有库存大于零时才能扣减；如果业务并发和一致性要求更高，还可以在事务中使用行锁，或者增加 version 字段实现乐观锁。

## TripStar AI：异步任务状态

面试官可能问：

> AI 任务完成和用户取消同时发生，状态怎么保证？

你可以回答：

> 更新时不能只根据任务 ID 无条件覆盖，而应该带上旧状态。例如只有任务仍然是 generating 时，才能更新为 completed。如果用户已经取消，完成回调更新时受影响行数为 0，就不再覆盖取消状态。

```sql
-- 只有任务仍处于生成中时，才允许更新为生成完成
UPDATE trip_tasks
SET status = 'completed',  -- 将任务状态修改为已完成
    updated_at = NOW()     -- 更新任务修改时间
WHERE id = 3001            -- 指定目标任务
  AND status = 'generating'; -- 确保任务没有被用户取消
```

这其实也是一种轻量级乐观并发控制。

# 二十四、本章必须背下来的六段答案

## 1. 什么是事务？

> 事务是一组不可分割的数据库操作，要么全部成功提交，要么全部失败回滚，主要用于保证多个相关操作之间的数据一致性。

## 2. ACID 是什么？

> ACID 分别是原子性、一致性、隔离性和持久性。原子性保证事务全部成功或全部失败；一致性保证事务前后数据规则合法；隔离性减少并发事务之间的相互影响；持久性保证事务提交后的结果不会轻易丢失。

## 3. 三种并发问题是什么？

> 脏读是读取到其他事务尚未提交的数据；不可重复读是同一事务两次读取同一行得到不同结果；幻读是相同范围条件两次查询，返回的数据行数量不同。

## 4. 四种隔离级别是什么？

> 从低到高分别是读未提交、读已提交、可重复读和串行化。隔离级别越高，并发异常越少，但并发处理成本通常也越高。

## 5. 什么是 MVCC？

> MVCC 是多版本并发控制。InnoDB 通过事务 ID、Undo Log 保存的历史版本以及 Read View 可见性判断，让不同事务读取适合自己的数据版本，从而减少读写阻塞，提高并发性能。

## 6. 乐观锁和悲观锁有什么区别？

> 悲观锁认为冲突很可能发生，所以先加锁再修改；乐观锁认为冲突较少，通常使用 version 版本号，在提交更新时检查数据是否被其他事务修改。

# 二十五、一分钟知识链

```text
多个 SQL 必须共同成功
        ↓
使用事务

        ↓

        ↓

```

# 二十六、本章闯关题

## 第 1 题

创建订单成功，但扣库存失败，应该怎么办？

答案：

> 创建订单和扣库存应放在同一个事务中，任何一步失败都应该回滚。

------

## 第 2 题

事务 A 读取到了事务 B 尚未提交的数据，这是什么？

答案：

> 脏读。

------

## 第 3 题

事务中两次查询同一个订单，状态从待支付变成已支付，这是什么？

答案：

> 不可重复读。

------

## 第 4 题

两次查询待支付订单，第一次 10 条，第二次 11 条，这是什么？

答案：

> 幻读。

------

## 第 5 题

MVCC 是不是完全不需要锁？

答案：

> 不是。MVCC 主要优化普通读取和写入之间的并发，但更新、删除、加锁查询等当前读操作仍然需要锁。

------

## 第 6 题

订单已经退款，但旧请求又把它更新成进行中，怎么避免？

答案：

> 更新时带上旧状态条件或 version 版本号，只有数据仍然处于预期状态时才允许修改。
