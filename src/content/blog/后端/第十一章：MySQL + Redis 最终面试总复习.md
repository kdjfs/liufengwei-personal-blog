# 二、MySQL 第一核心：索引

## 1. 索引到底是什么？

不要只背：

> 索引是提高查询效率的数据结构。

你应该回答：

> 索引本质是用额外的存储空间和写入维护成本，换取查询效率。InnoDB 的索引主要使用 B+ 树，通过有序的数据结构减少需要扫描的数据量。

这里最重要的不是：

> “有索引就快。”

而是：

> **索引的本质是减少扫描。**

------

# 三、为什么 InnoDB 用 B+ 树？

标准高质量答案：

> B+ 树具有较高的扇出，一个节点能够保存很多索引项，因此即使数据量很大，树高通常也比较低，可以减少磁盘页访问次数。同时非叶子节点主要用于索引导航，完整数据集中在叶子节点，叶子节点又按顺序连接，因此既适合等值查询，也非常适合范围查询、排序和顺序扫描。

面试官追问：

> 为什么不用二叉树？

你回答：

> 二叉树一个节点最多两个子节点，数据量大时树高容易增加，而数据库一次磁盘 IO 成本远高于内存比较成本，所以数据库更希望用“矮而胖”的树减少 IO 次数。

这就不是只会背“B+树”了。

------

# 四、聚簇索引、二级索引、回表

这是必须彻底明白的。

InnoDB：

```text
主键索引
    ↓
B+树叶子节点
    ↓
完整行数据
```

所以主键索引通常是：

> **聚簇索引。**

普通索引：

```text
name 索引
    ↓
B+树叶子节点
    ↓
name + 主键 id
```

查询：

```sql
-- 根据姓名查询用户完整信息
SELECT *
FROM users
WHERE name = '刘凤伟'; -- name 假设建立了普通索引
```

过程：

```text
先查询 name 二级索引
       ↓
获得主键 ID
       ↓
再查询主键索引
       ↓
获得完整用户数据
```

这就是：

> **回表。**

------

# 五、覆盖索引

如果：

```sql
-- 只查询普通索引本身以及主键字段
SELECT
  id,   -- 主键通常存在于二级索引叶子节点
  name  -- 当前二级索引字段
FROM users
WHERE name = '刘凤伟'; -- 根据 name 索引查询
```

二级索引已经包含需要的全部字段。

因此：

> 不需要回表。

这叫覆盖索引。

### 面试加分点

不要说：

> `SELECT *` 会导致索引失效。

这是错误的。

正确：

> `SELECT *` 不一定导致索引失效，但是容易让查询无法使用覆盖索引，从而增加回表和 IO。

# 六、联合索引和最左前缀

比如订单查询：

```sql
-- 查询某个用户指定状态下的最新订单
SELECT
  id,          -- 订单 ID
  order_no,    -- 订单编号
  created_at   -- 创建时间
FROM orders
WHERE user_id = 1001      -- 第一个等值查询条件
  AND status = 20         -- 第二个等值查询条件
ORDER BY created_at DESC  -- 最后按照时间排序
LIMIT 20;                 -- 只返回最新 20 条
```

可以设计：

```sql
-- 建立用户、状态、创建时间联合索引
CREATE INDEX idx_user_status_created
ON orders (
  user_id,    -- 第一列：用户
  status,     -- 第二列：状态
  created_at  -- 第三列：时间
);
```

排列逻辑：

```text
先 user_id
    ↓
user_id 相同时按 status
    ↓
前两者相同时按 created_at
```

所以：

```text
(a,b,c)

a             ✅
a,b           ✅
a,b,c         ✅
b,c           ❌ 无法充分利用最左前缀
a,c           ✅ 可以利用 a，但 c 不能直接跨过 b 完整用于定位
```

要特别记住：

> WHERE 中字段书写顺序不决定联合索引是否生效，优化器可以调整条件。真正重要的是索引自身的字段顺序。

# 七、索引失效不要背成绝对规则

你应该知道几个高频风险：

### 对索引列做函数计算

```sql
-- 不推荐：对索引列执行函数，可能影响普通索引使用
SELECT
  id,          -- 订单 ID
  created_at   -- 创建时间
FROM orders
WHERE DATE(created_at) = '2026-08-02'; -- 对 created_at 做函数计算
```

更好：

```sql
-- 推荐：直接按照时间范围进行查询
SELECT
  id,          -- 订单 ID
  created_at   -- 创建时间
FROM orders
WHERE created_at >= '2026-08-02 00:00:00' -- 包含当天零点
  AND created_at < '2026-08-03 00:00:00'; -- 不包含第二天零点
```

### 前置 `%`

```sql
-- 已知字符串开头，更容易利用普通 B+ 树索引
SELECT
  id,       -- 用户 ID
  name      -- 用户名称
FROM users
WHERE name LIKE '刘%'; -- 前缀确定
```

而：

```sql
-- 前缀未知，普通 B+ 树通常难以快速定位起点
SELECT
  id,       -- 用户 ID
  name      -- 用户名称
FROM users
WHERE name LIKE '%凤伟%'; -- 开头就是通配符
```

### 隐式类型转换

数据库是：

```text
phone VARCHAR
```

查询尽量写：

```sql
-- phone 是字符串字段，因此使用字符串进行比较
SELECT
  id,       -- 用户 ID
  phone     -- 手机号
FROM users
WHERE phone = '15118978572'; -- 类型与数据库字段一致
```

# 八、MySQL 第二核心：事务

一句话理解：

> **事务就是一组 SQL，要么一起成功，要么一起失败。**

例如：

```text
创建订单
+
扣库存
```

不能出现：

```text
订单创建成功
库存扣减失败
```

事务：

```sql
-- 开启数据库事务
START TRANSACTION;

-- 创建订单
INSERT INTO orders (
  order_no,   -- 订单编号
  user_id     -- 用户 ID
)
VALUES (
  'ORDER001', -- 新订单编号
  1001        -- 下单用户
);

-- 在库存大于 0 时扣减库存
UPDATE products
SET stock = stock - 1 -- 库存减一
WHERE id = 2001       -- 指定商品
  AND stock > 0;      -- 保证库存不会直接扣成负数

-- 所有操作成功后正式提交
COMMIT;
```

失败：

```sql
-- 事务过程中出现异常时撤销本次修改
ROLLBACK;
```

# 九、ACID 必须能脱口而出

```text
A Atomicity     原子性
C Consistency   一致性
I Isolation     隔离性
D Durability    持久性
```

推荐回答：

> 原子性保证事务中的操作要么全部成功要么全部失败；一致性保证事务执行前后数据符合业务规则；隔离性处理并发事务之间的相互影响；持久性保证已经提交的数据能够可靠保存。

# 十、这里补一个前十章没重点讲、但很值得知道的东西

## Undo Log 和 Redo Log

### Undo Log

主要解决：

> **后悔怎么办？**

执行：

```text
stock：10 → 9
```

Undo Log 会记录修改前的信息。

作用：

- 事务回滚；
- MVCC 历史版本。

记忆：

> **Undo = 撤销。**

------

## Redo Log

主要解决：

> **已经提交，但服务器突然断电怎么办？**

数据库修改通常先操作内存页，如果每个事务都马上随机写磁盘数据页，成本很高。

Redo Log 会记录：

> 哪些修改已经做过。

宕机恢复时可以根据 Redo Log 恢复已提交事务。

记忆：

> **Redo = 重做。**

非常漂亮的一句回答：

> Undo Log 主要保证回滚能力并支持 MVCC，解决“修改了但需要撤销”的问题；Redo Log 记录已经完成的修改，用于崩溃恢复，是事务持久性的重要基础。

# 十一、binlog 要不要会？

你是前端，不需要深入。

只知道：

> binlog 是 MySQL Server 层的逻辑日志，常用于主从复制、数据恢复等。

区别：

```text
Undo Log
回滚 + MVCC

Redo Log
InnoDB 崩溃恢复

Binlog
Server 层归档 / 主从复制 / 数据恢复
```

这已经够你面前端实习。

# 十二、隔离级别必须背

从低到高：

```text
Read Uncommitted
读未提交

Read Committed
读已提交

Repeatable Read
可重复读

Serializable
串行化
```

并发问题：

### 脏读

> 读到了别人没有提交的数据。

### 不可重复读

> 同一个事务，两次读同一行结果不同。

### 幻读

> 相同条件范围查询，前后数据行发生变化。

一句话：

> **脏读是读了未提交；不可重复读是一行变了；幻读是一批数据变了。**

------

# 十三、MVCC 是面试里必须讲漂亮的地方

不要只说：

> MVCC 就是多版本并发控制。

完整答案：

> MVCC 是 InnoDB 用来提高并发读写性能的一套多版本并发控制机制。数据修改时通过 Undo Log 保留历史版本，并结合事务 ID 和 Read View 判断当前事务能够看到哪个版本。这样普通 SELECT 可以读取符合自身可见性规则的历史版本，不需要和写事务互相长时间阻塞。

关键结构：

```text
Undo Log
    +
事务 ID
    +
Read View
    ↓
判断版本可见性
```

核心价值：

> **让读和写尽量互不阻塞。**

------

# 十四、快照读 vs 当前读

普通：

```sql
-- 普通 SELECT 一般属于快照读，会根据 MVCC 可见性读取数据
SELECT
  id,      -- 订单 ID
  status   -- 订单状态
FROM orders
WHERE id = 1001; -- 查询指定订单
```

属于：

> 快照读。

而：

```sql
-- 查询最新数据，同时对目标记录加排他锁
SELECT
  id,      -- 订单 ID
  stock    -- 当前库存
FROM products
WHERE id = 2001 -- 指定商品
FOR UPDATE;     -- 当前读，并加排他锁
```

属于：

> 当前读。

------

# 十五、MySQL RR 为什么还能处理幻读？

这是进阶加分点。

MySQL InnoDB 默认常见隔离级别是：

> Repeatable Read。

它除了使用 MVCC 解决快照读的一致性，在加锁的当前读场景中还会使用：

> **Record Lock + Gap Lock → Next-Key Lock**

简单理解：

```text
Record Lock
锁住已经存在的记录

Gap Lock
锁住记录之间的间隙

Next-Key Lock
记录锁 + 间隙锁
```

例如查询：

```sql
-- 锁定金额处于指定范围的数据，用于演示范围当前读
SELECT
  id,      -- 订单 ID
  amount   -- 订单金额
FROM orders
WHERE amount > 100  -- 查询范围
  AND amount < 200  -- 查询范围
FOR UPDATE;          -- 当前读并加锁
```

InnoDB 不只是锁已有的记录，还可能锁一定范围的间隙，阻止其他事务往相关范围插入数据，从而降低幻读问题。

你不用深入算法。

面试官问到可以回答：

> InnoDB 的 RR 不只是靠 MVCC。快照读主要依赖 MVCC，而当前读还会结合 Record Lock、Gap Lock 和 Next-Key Lock 来限制相关范围的插入，因此能较好处理幻读。

这句话很加分。

# 十六、乐观锁 vs 悲观锁

### 悲观锁

> 我觉得别人一定会和我抢，所以先锁住。

```sql
-- 查询商品最新库存，并锁住目标记录
SELECT
  id,     -- 商品 ID
  stock   -- 当前库存
FROM products
WHERE id = 2001 -- 指定商品
FOR UPDATE;     -- 添加排他锁
```

### 乐观锁

> 我先不锁，提交修改时检查版本。

```sql
-- 只有版本号仍然为 5 时才允许更新
UPDATE products
SET
  stock = stock - 1,   -- 库存减一
  version = version + 1 -- 更新版本号
WHERE id = 2001        -- 指定商品
  AND stock > 0        -- 保证库存充足
  AND version = 5;     -- 保证数据没有被其他请求修改
```

一句话：

> 悲观锁是先锁再改，乐观锁是修改时检测冲突。

# 十七、真正优秀的库存扣减写法

不要写：

```text
SELECT stock
判断 > 0
UPDATE stock - 1
```

因为两个请求可能同时读到库存 1。

更好：

```sql
-- 只有库存仍然大于零时，数据库才会完成扣减
UPDATE products
SET stock = stock - 1 -- 原子扣减库存
WHERE id = 2001      -- 指定商品
  AND stock > 0;     -- 保证库存不能被扣成负数
```

然后：

```text
affectedRows = 1
成功

affectedRows = 0
库存不足
```

这种：

> **利用数据库条件更新保证原子性**

非常值得在面试中说。

# 十八、MySQL 第三核心：慢 SQL

如果面试官问：

> SQL 很慢怎么排查？

别只说：

> 加索引。

满分思路：

```text
1. 先确定是不是数据库慢
2. 找到具体 SQL
3. EXPLAIN 分析执行计划
4. 看 type
5. 看 key
6. 看 rows
7. 看 Extra
8. 检查索引
9. 检查 SQL 写法
10. 优化后重新测试
```

标准回答：

> 我会先判断耗时到底发生在前端渲染、网络、后端业务还是数据库。如果确认 SQL 较慢，再通过慢查询日志找到 SQL，并使用 EXPLAIN 查看 type、实际使用的 key、预计扫描 rows 和 Extra。之后重点检查联合索引设计、回表、函数计算、前置模糊查询、隐式类型转换、额外排序、深分页、N+1 和返回数据量，最后通过实际执行时间验证优化效果。

这段建议背下来。

```text
大表
+

+

```

# 二十一、深分页一定会被问

普通：

```sql
-- 跳过前十万条，再查询十条
SELECT
  id,          -- 订单 ID
  order_no     -- 订单编号
FROM orders
ORDER BY id DESC -- 按主键倒序
LIMIT 100000, 10; -- 深分页
```

数据库可能需要：

```text
扫描 100010 条
丢掉前 100000
留下 10 条
```

游标分页：

```sql
-- 根据上一页最后一条记录 ID 查询下一页
SELECT
  id,          -- 订单 ID
  order_no     -- 订单编号
FROM orders
WHERE id < 88888 -- 上一页最后一个 ID
ORDER BY id DESC -- 按 ID 倒序
LIMIT 10;        -- 只获取下一页十条
```

前端也应该理解：

> 无限滚动、消息流、订单流适合 cursor / lastId，而后台需要任意跳页时 page/pageSize 更方便。

# 二十二、N+1 问题

错误：

```js
// 先查询 100 条订单
const orders = await getOrders();

// 遍历 100 条订单
for (const order of orders) {
  // 每条订单都再请求一次数据库查询用户
  order.user = await getUserById(order.userId);
}
```

数据库：

```text
1 + 100 = 101 次查询
```

解决：

> JOIN / 批量 IN / ORM 预加载。

# 二十三、SQL 注入——前端转全栈最好会

不要拼字符串：

```js
// 错误示例：直接拼接用户输入，存在 SQL 注入风险
const sql =
  "SELECT * FROM users WHERE username = '" +
  username +
  "'";
```

应该参数化：

```js
// 使用参数化 SQL，将用户输入与 SQL 结构分离
const [rows] = await pool.execute(
  `
    -- 根据用户名查询用户
    SELECT
      id,        -- 用户 ID
      username   -- 用户名
    FROM users
    WHERE username = ? -- 使用占位符，不直接拼接用户输入
  `,
  [username], // 数据库驱动负责安全处理参数
);
```

# 二十四、Redis 第一核心：五种数据类型

| String | 一个 Key 一个 Value | Token、验证码、缓存、计数 |

# 二十五、Redis 为什么快？

标准答案：

> Redis 的主要数据存放在内存中，避免大量磁盘随机 IO；同时内部数据结构针对不同场景高度优化，命令执行路径相对简单，并采用事件驱动和 IO 多路复用处理大量连接。Redis 核心命令执行主要保持顺序性，减少线程切换和锁竞争，但 Redis 整体并不是所有工作都只有一个线程。

这一段非常值得背。

# 二十六、Cache Aside 是 Redis 最重要的业务模式

读取：

```text
查 Redis
   ↓
有 → 返回

没有
 ↓
查 MySQL
 ↓
写 Redis
 ↓
返回
```

写：

```text
更新 MySQL
    ↓
删除 Redis
```

不是：

```text
更新 MySQL
+
更新 Redis
```

主要原因：

> 并发情况下两个请求更新缓存的完成顺序可能与数据库顺序不一致，旧缓存可能覆盖新缓存。

所以：

> **缓存更适合失效，而不是复杂地同步修改。**

# 二十七、Redis 和 MySQL 一致性标准答案

建议整段背：

> 在 Cache Aside 模式下，读取时先查 Redis，未命中再查 MySQL 并回填缓存；更新时通常先更新 MySQL，再删除 Redis。这样可以降低并发场景下旧缓存覆盖新数据的风险。不过缓存和数据库很难做到绝对强一致，一般通过合理 TTL、删除失败重试、消息队列补偿等机制保证最终一致性。

非常高频。

# 二十八、为什么不是“先删 Redis，再更新 MySQL”？

并发场景：

```text
请求 A 删除 Redis
          ↓
请求 B 查询 Redis：没有
          ↓
请求 B 查询 MySQL：旧数据
          ↓
请求 B 将旧数据写 Redis
          ↓
请求 A 更新 MySQL
```

结果：

```text
MySQL：新
Redis：旧
```

所以一般：

> 先更新数据库，再删除缓存。

注意：

> 也不是绝对不会有问题，只是通常风险窗口更合理。

# 三十三、RDB 和 AOF

口诀：

> **RDB 拍照片，AOF 写日记。**

### RDB

定期保存整个数据快照。

优点：

- 文件紧凑；
- 恢复快。

缺点：

- 两次快照之间的数据可能丢失。

### AOF

记录写操作。

优点：

- 数据丢失窗口通常更小。

缺点：

- 文件更大；
- 恢复可能更慢；
- 需要 AOF Rewrite。

标准答案：

> RDB 是时间点快照，适合备份和快速恢复，但可能丢失快照间的数据；AOF 持续记录写命令，数据完整性通常更高，但文件更大，需要通过重写控制体积。实际系统可以根据数据重要性结合使用。

# 三十四、热 Key vs 大 Key

- 网络带宽；
- 击穿。

解决：

- 本地缓存；
- 副本分散；
- 预热；
- 不物理过期；
- 限流。

## 大 Key

> Value 很大或集合元素很多。

危险：

- 占内存；
- 网络传输慢；

解决：

- 拆分；
- 分页；
- 避免一次读全部；
- 大 Key 删除考虑 `UNLINK`。

口诀：

> **热 Key 是人太多，大 Key 是东西太重。**

# 三十六、为什么 Value 必须使用唯一 Token？

# 三十七、为什么解锁要 Lua？

不能：

```text
GET
判断
DEL
```

因为两条命令之间锁可能变化。

Lua：

```lua
-- 判断当前锁是否仍然属于当前请求
if redis.call('GET', KEYS[1]) == ARGV[1] then
  -- 属于当前请求时才删除锁
  return redis.call('DEL', KEYS[1])
else
  -- 已经不属于当前请求时不能删除
  return 0
end
```

作用：

> **判断 + 删除原子执行。**

谁成功。


失败。

这是比“Redis 加个锁”更可靠的回答。

# 四十七、面试官连续拷打模拟 1：MySQL

### 面试官

MySQL 索引为什么用 B+ 树？

### 你

> B+ 树扇出高、树高低，可以减少磁盘 IO；非叶子节点主要用于索引导航，叶子节点保存数据并且有序连接，所以同时适合等值查询、范围查询和排序。

### 面试官

什么叫回表？

### 你

> InnoDB 二级索引叶子节点通常保存索引字段和主键，如果查询字段没有完全被二级索引覆盖，就要根据主键再查询聚簇索引获取完整行，这叫回表。

### 面试官

怎么避免？

### 你

> 可以针对高频查询设计覆盖索引，并避免无意义的 `SELECT *`，但不能为了覆盖索引把大量业务字段全部塞入索引，因为索引本身也有存储和写入维护成本。

这最后一句非常加分。

# 四十八、面试官连续拷打模拟 2：事务

### 面试官

MVCC 是什么？

### 你

> MVCC 是多版本并发控制。InnoDB 通过 Undo Log 保存历史版本，通过事务 ID 和 Read View 判断当前事务能够看到哪个版本，使普通查询很多时候不需要和写事务互相阻塞。

### 面试官

那是不是完全不需要锁？

### 你

> 不是。MVCC 主要解决快照读的并发问题，而 UPDATE、DELETE、SELECT FOR UPDATE 等当前读仍然需要锁。

### 面试官

RR 怎么处理幻读？

### 你

> 快照读主要依赖 MVCC，而加锁当前读会结合 Record Lock、Gap Lock 和 Next-Key Lock 对记录和一定范围加锁，从而限制其他事务向相关范围插入数据。

这一套已经明显超过“了解 MySQL”的最低要求。

# 四十九、面试官连续拷打模拟 3：Redis

### 面试官

Redis 为什么快？

### 你

> 数据主要在内存，高效数据结构，命令执行路径简单，加上事件驱动和 IO 多路复用；核心命令执行主要保持顺序性，也减少了线程切换和锁竞争。

### 面试官

为什么不能所有东西都放 Redis？

### 你

> Redis 内存成本更高，也不擅长复杂关系查询和完整事务业务。订单、支付、用户、正式行程等核心数据仍应该保存在 MySQL，Redis 更适合作为缓存和临时高频数据存储。

### 面试官

Redis 持久化以后也不行吗？

### 你

> RDB 和 AOF 提升的是 Redis 的恢复能力，不会改变 Redis 的数据模型和主要定位，所以持久化不等于 Redis 就能替代 MySQL。

很好。

# 五十一、真正需要你背下来的 15 个问题

如果时间极限，只背这些。

## MySQL

**1. MySQL 索引为什么使用 B+ 树？**

> 扇出高、树高低、减少 IO，叶子节点有序连接，支持等值、范围和排序。

**2. 什么是回表？**

> 二级索引找到主键后，再查询聚簇索引获取完整行数据。

**3. 什么是覆盖索引？**

> 查询需要的所有字段都能直接从索引获取，不需要回表。

**4. 什么是最左前缀？**

> 联合索引从最左列开始连续匹配才能充分利用索引。

**5. 什么是 ACID？**

> 原子性、一致性、隔离性、持久性。

**6. 什么是 MVCC？**

> Undo Log + 事务 ID + Read View 管理数据多个版本，减少读写阻塞。

**7. 乐观锁和悲观锁区别？**

> 悲观锁先锁再修改；乐观锁更新时通过 version 或旧状态检查冲突。

**8. SQL 慢怎么优化？**

> 定位 SQL → EXPLAIN → type/key/rows/Extra → 索引 → SQL 改写 → 验证。

------

## Redis

**9. Redis 为什么快？**

> 内存 + 高效数据结构 + IO 多路复用 + 简单执行模型。

**10. 五种类型？**

> String、Hash、List、Set、ZSet。

**11. Redis + MySQL 怎么配合？**

> Cache Aside：先 Redis，Miss 查 MySQL 回填；写入时先更新 MySQL，再删 Redis。

**12. 穿透、击穿、雪崩？**

> 不存在 / 一个热点 / 大量失效。

**13. RDB 和 AOF？**

> 快照 vs 写日志。

**14. Redis 分布式锁？**

> `SET key token NX EX`，Token 唯一，Lua 判断 Token 后删除。

**15. 幂等怎么实现？**

> 幂等 Key + Redis 快速拦截 + 数据库唯一索引/状态机最终兜底。

```text
================ MySQL ================

1. 索引
B+树：矮胖、IO少、支持范围查询

主键索引：
叶子节点保存完整行

二级索引 → 主键 → 完整数据

数据直接从索引拿，不回表

遵循最左前缀

原子、一致、隔离、持久

Undo Log：
回滚 + MVCC

Redo Log：
崩溃恢复

MVCC：
Undo Log + 事务ID + Read View

快照读：
普通 SELECT

当前读：
UPDATE / DELETE / FOR UPDATE


3. 锁

悲观锁：
先锁再改

乐观锁：
version / 旧状态条件

重要业务：
条件更新 + 唯一索引 + 事务兜底


4. SQL 优化

EXPLAIN：
type
key
rows
Extra

重点排查：
索引
SELECT *
函数
前置 %
隐式转换
深分页
N+1
大量返回数据


================ Redis ================

1. 五种类型

String：
缓存、Token、验证码、计数

Hash：
对象

List：
队列、最近记录

Set：
去重、点赞

ZSet：
排行榜


2. Cache Aside

读：
Redis → MySQL → 回填 Redis
```

最后我希望你真正记住的不是 100 个术语，而是这六句话：

> **索引的本质，是减少扫描。**

> **事务的本质，是保证一组操作的数据正确性。**

> **MVCC 的本质，是让读写尽量不要互相阻塞。**

> **Redis 的本质，是用内存换取高性能。**

> **缓存的本质，是数据库数据的副本，所以允许失效和重建。**

> **Redis 可以挡住大量并发，但核心业务最终一定要让数据库约束、事务和状态机兜底。**

你把这六句话真正理解，再把上面的 15 道核心题背下来，你这一天的 MySQL + Redis 学习就已经完成了一个非常有价值的闭环。
