这一章把 Redis 想象成一家**速度极快但房间有限的酒店**：

- 内存：酒店房间，速度快但数量有限；
- 过期时间：住客退房时间；
- 淘汰策略：房间满了以后请谁离开；
- RDB、AOF：酒店的备份档案；
- 热 Key：一个房间门口挤了十万人；
- 大 Key：一个客人占了半栋楼。

你今天重点回答六个问题：

1. Redis 为什么快？
2. Key 过期后为什么不一定立刻消失？
3. 内存满了怎么办？
4. RDB 和 AOF 有什么区别？
5. 什么是热 Key？
6. 什么是大 Key？

------

# 一、Redis 为什么这么快？

面试时不要只回答：

> 因为 Redis 在内存中。

这只答了一部分。

Redis 快主要有四个原因。

## 原因一：主要操作内存

MySQL 的核心数据长期存储在磁盘中。

Redis 的主要数据放在内存里，CPU 访问内存的速度远快于磁盘随机读写。

可以想象成：

```text
MySQL：去仓库寻找资料
Redis：资料直接放在手边
```

但要注意：

> MySQL 也会使用内存缓存，Redis 快并不只是因为“内存”两个字。

------

## 原因二：数据结构经过专门优化

Redis 不只是简单的字符串仓库。

它提供：

```text
String
Hash
List
Set
ZSet
```

这些结构针对特定操作做了优化。

例如计数器：

```redis
# 将文章 2001 的浏览次数原子增加一
INCR article:2001:view_count
```

排行榜：

```redis
# 将用户 1001 的积分增加五分
ZINCRBY user:ranking 5 "1001"
```

不需要像 MySQL 一样执行复杂查询和排序逻辑。

------

## 原因三：命令执行路径比较简单

Redis 通常根据 Key 直接操作数据：

```redis
# 根据明确的 Key 查询用户缓存
GET user:detail:1001
```

而 MySQL 可能需要：

```text
解析 SQL
选择执行计划
寻找索引
进行回表
连接多张表
排序或分组
```

Redis 的大部分操作路径更直接。

------

## 原因四：IO 多路复用

Redis 可以使用一个事件循环同时管理大量网络连接。

你可以把它想象成餐厅中的一个高效服务员：

```text
客人 A：正在看菜单
客人 B：正在等厨房
客人 C：准备点餐
```

服务员不会一直站在客人 A 身边等待，而是哪个连接准备好了，就处理哪个。

这就是 IO 多路复用的核心思想。

------

# 二、Redis 是单线程吗？

这是一个高频陷阱题。

不要简单回答：

> Redis 就是单线程。

更准确的说法是：

> Redis 的核心命令执行长期以来主要采用单线程顺序处理，因此避免了大量线程切换和数据竞争；但 Redis 并不是所有工作都只有一个线程，新版本可以使用其他线程处理网络 IO、后台持久化和异步释放等任务。

你现在只记一句：

> **命令执行主要顺序进行，但 Redis 整体不等于只有一个线程。**

------

## 单线程为什么还能快？

因为 Redis 的主要瓶颈通常不是 CPU 计算，而是：

- 网络传输；
- 内存访问；
- 命令本身是否耗时。

同时，单线程命令执行减少了：

- 多线程上下文切换；
- 锁竞争；
- 并发修改数据结构的复杂性。

但是单线程也有弱点：

> 一个命令执行太久，后面的命令都可能被堵住。

例如，不要随便对超大集合执行一次性全量操作。

------

## Redis 为什么快——标准答案

> Redis 的数据主要存放在内存中，访问速度快；内部数据结构和命令实现经过专门优化；核心命令执行路径相对简单，并通过事件驱动和 IO 多路复用处理大量连接。Redis 的命令执行主要保持顺序性，减少了线程切换和锁竞争，但持久化、网络 IO 等环节并不一定只有一个线程。

这段建议背下来。

------

# 三、Key 过期后，会立刻删除吗？

不一定。

假设验证码设置五分钟过期：

```redis
# 保存手机验证码，并设置 300 秒后过期
SET verify:phone:15118978572 "683921" EX 300
```

五分钟后，这个 Key 在逻辑上已经不能使用。

但 Redis 不一定在第 300 秒一到，就立刻冲过去删除它。

因为如果给每个 Key 都创建一个精准定时器：

```text
1000 万个 Key
=
1000 万个定时任务
```

管理成本会非常高。

Redis 通常结合两种方式删除过期 Key：

1. 惰性删除；
2. 定期删除。

------

# 四、惰性删除：有人来查时才检查

假设 Key 已经过期，但仍暂时占着内存。

当请求访问它时：

```redis
# 查询已经到期的验证码
GET verify:phone:15118978572
```

Redis 发现：

```text
这个 Key 已经过期
```

于是将其删除，并返回不存在。

这叫：

> **惰性删除。**

像酒店住客退房时间到了，但前台暂时没检查；直到有人来订这个房间，才发现原住客应该离开了。

------

## 惰性删除的问题

如果一个过期 Key 永远没人访问：

```text
它可能还会暂时占用内存
```

所以仅靠惰性删除不够。

------

# 五、定期删除：Redis 主动抽查

Redis 会周期性随机抽取一部分设置了过期时间的 Key：

```text
抽查一批 Key
    ↓
发现已经过期
    ↓
进行删除
```

它不是每次扫描全部 Key，因为全量扫描成本太高。

这叫：

> **定期删除。**

------

## 为什么两种策略结合？

惰性删除负责：

> 使用时及时发现过期。

定期删除负责：

> 清理那些很久没人访问的过期 Key。

面试答案：

> Redis 的过期 Key 通常不是到期后立刻全部删除，而是结合惰性删除和定期删除。惰性删除在访问 Key 时判断是否过期，定期删除则周期性抽样清理过期 Key，从而在 CPU 消耗和内存释放之间取得平衡。

------

# 六、TTL 到期和内存淘汰不是一回事

这两个概念很容易混淆。

## 过期删除

Key 自己设置了寿命：

```redis
# 保存登录状态，并设置两小时后过期
SET login:token:abc123 "1001" EX 7200
```

两小时后应该被删除。

## 内存淘汰

Redis 内存已经接近上限，即使有些 Key 还没有过期，也可能需要选择一部分数据清除。

一句话：

> **过期删除是寿命到了，内存淘汰是房间不够了。**

------

# 七、Redis 内存满了怎么办？

Redis 可以配置最大可使用内存：

```text
maxmemory
```

当内存达到上限后，Redis 会根据：

> ```
> maxmemory-policy
> ```

选择处理方式。

你不需要把所有策略源码背下来，但需要掌握主要类型。

------

# 八、noeviction：谁都不赶，拒绝新写入

`noeviction` 的意思是：

> 不主动淘汰现有数据。

内存满后：

- 查询操作仍可能继续；
- 新增或扩大内存的写操作可能报错。

可以理解为：

> 酒店住满了，不赶走任何客人，拒绝新客入住。

优点：

- 不会因为淘汰导致已有数据突然消失。

缺点：

- 新写入可能失败。

适合不能随便丢数据、需要调用方明确处理异常的场景。

------

# 九、LRU：优先淘汰最近最少使用的数据

LRU 全称：

> Least Recently Used，最近最少使用。

假设三个 Key：

```text
Key A：刚刚访问过
Key B：一分钟前访问
Key C：三天没访问
```

LRU 更倾向淘汰：

```text
Key C
```

因为它最近最少被使用。

记忆：

> **LRU 看“多久没来过”。**

常见策略包括：

```text
allkeys-lru
volatile-lru
```

## allkeys-lru

从所有 Key 中选择最近最少使用的数据淘汰。

## volatile-lru

只从设置了过期时间的 Key 中淘汰最近最少使用的数据。

------

# 十、LFU：优先淘汰访问频率最低的数据

LFU 全称：

> Least Frequently Used，最不经常使用。

假设：

```text
Key A：一天访问 10000 次
Key B：一天访问 100 次
Key C：一天访问 2 次
```

LFU 更倾向淘汰：

```text
Key C
```

记忆：

> **LFU 看“来过多少次”。**

常见策略：

```text
allkeys-lfu
volatile-lfu
```

------

# 十一、LRU 和 LFU 的区别

## LRU

关注：

> 最近一次是什么时候访问的？

例如某条新闻昨天很火，今天完全没人看，它可能逐渐被淘汰。

## LFU

关注：

> 一段时间内访问频率有多高？

例如系统配置长期稳定地被频繁访问，更容易保留下来。

一句话：

> **LRU 看时间，LFU 看次数。**

------

# 十二、Random 和 TTL 淘汰

## Random

随机选择数据淘汰：

```text
allkeys-random
volatile-random
```

简单，但不一定能留下真正有价值的热点数据。

## volatile-ttl

从设置了过期时间的 Key 中，优先淘汰剩余寿命更短的数据。

例如：

```text
Key A：还剩 10 秒
Key B：还剩 10 分钟
```

更可能先淘汰 Key A。

------

# 十三、淘汰策略怎么选择？

你可以这样理解：

| 策略         | 核心含义                        | 适合场景          |
| ------------ | ------------------------------- | ----------------- |
| noeviction   | 内存满后拒绝写入                | 数据不能随便丢    |
| allkeys-lru  | 淘汰最近最少使用的 Key          | 通用缓存          |
| allkeys-lfu  | 淘汰使用频率最低的 Key          | 热点差异明显      |
| volatile-lru | 只在有 TTL 的 Key 中按 LRU 淘汰 | 永久数据不能淘汰  |
| volatile-ttl | 优先淘汰快过期的 Key            | 有明确 TTL 的缓存 |

面试中一般不要求你说出绝对最优答案。

更专业的说法是：

> 淘汰策略要结合 Redis 中是否全部都是缓存、哪些数据允许丢失、访问是否存在明显热点以及业务对写入失败的容忍度选择。通用缓存场景常考虑 allkeys-lru 或 allkeys-lfu，但不能脱离业务直接断言某一种策略永远最好。

------

# 十四、Redis 断电后，数据会全部消失吗？

如果 Redis 只依靠内存，并且完全没有持久化：

```text
进程退出或机器断电
    ↓
内存数据消失
```

Redis 提供了两种主要持久化机制：

1. RDB；
2. AOF。

持久化的目的：

> 把内存中的数据保存到磁盘，重启时用于恢复。

------

# 十五、RDB：定期拍一张全家福

RDB 可以理解为：

> 在某个时间点，把 Redis 数据整体生成一个快照文件。

例如：

```text
12:00 拍一次快照
12:10 拍一次快照
12:20 拍一次快照
```

如果 12:18 Redis 崩溃，只能使用 12:10 的最近快照恢复，那么：

```text
12:10 到 12:18 的部分数据可能丢失
```

------

## RDB 的优点

- 文件紧凑；
- 适合备份；
- 恢复速度通常较快；
- 对主线程日常命令执行影响相对可控。

## RDB 的缺点

- 两次快照之间的数据可能丢失；
- 数据量大时，生成快照需要额外资源；
- 通常不适合要求极低数据丢失窗口的场景。

------

## RDB 故事记忆

你每天晚上十二点给作业拍照。

第二天下午电脑坏了。

你只能恢复到昨晚的照片，今天新增的内容可能丢失。

这就是 RDB。

------

# 十六、AOF：把每一步操作记在账本里

AOF 全称：

> Append Only File，追加日志文件。

Redis 会把写命令按照顺序记录下来。

例如执行：

```redis
# 保存用户姓名
SET user:1001:name "刘凤伟"

# 将文章浏览量增加一
INCR article:2001:view_count

# 删除旧的用户缓存
DEL user:detail:1001
```

AOF 会记录相应写操作。

Redis 重启后，可以重新执行这些操作恢复数据。

------

## AOF 的优点

- 数据丢失窗口通常比单纯 RDB 更小；
- 写操作有连续日志；
- 数据恢复更细致。

## AOF 的缺点

- 文件通常比 RDB 大；
- 恢复时可能需要重放大量命令；
- 频繁写磁盘会带来额外开销；
- 需要进行 AOF 重写压缩日志。

------

# 十七、AOF 为什么需要重写？

假设浏览量被修改了一万次：

```redis
# 将浏览量增加一，实际业务中可能执行很多次
INCR article:2001:view_count
```

AOF 里可能记录了一万条命令。

但恢复最终状态时，也许只需要：

```redis
# 直接恢复文章当前的最终浏览量
SET article:2001:view_count "10000"
```

AOF 重写会根据当前数据状态，生成更精简的日志。

目的：

- 减少文件体积；
- 加快恢复；
- 删除无意义的历史操作。

------

# 十八、AOF 的三种刷盘策略

你只需要理解三档。

## always

每次写命令都尽快同步到磁盘。

优点：

- 数据安全性较高。

缺点：

- 性能开销较大。

## everysec

通常每秒进行一次同步。

优点：

- 性能与数据安全之间比较平衡。

风险：

- 极端故障下可能丢失大约最近一小段时间的数据。

这是常见选择。

## no

由操作系统决定什么时候同步磁盘。

优点：

- 性能较好。

缺点：

- 数据丢失窗口更难控制。

记忆：

```text
always：每笔都记
everysec：每秒记一次
no：交给操作系统
```

------

# 十九、RDB 和 AOF 的区别

| 对比项     | RDB                      | AOF                    |
| ---------- | ------------------------ | ---------------------- |
| 核心方式   | 定期保存数据快照         | 持续记录写命令         |
| 文件大小   | 通常较小                 | 通常较大               |
| 恢复速度   | 通常较快                 | 需要重放命令，可能较慢 |
| 数据完整性 | 可能丢失两次快照间的数据 | 通常丢失更少           |
| 适合方向   | 备份、快速恢复           | 降低数据丢失窗口       |

最简单记忆：

> **RDB 是拍照，AOF 是记日记。**

------

# 二十、RDB 和 AOF 应该选哪个？

不是永远只能二选一。

实际项目可以：

- 只使用 RDB；
- 只使用 AOF；
- 两者结合；
- Redis 只是可重建缓存时，降低持久化要求。

如果 Redis 中只是 MySQL 缓存：

```text
Redis 丢失
   ↓
重新从 MySQL 加载
```

这时持久化要求可能没那么高。

如果 Redis 保存了一些难以重建的数据，例如实时计数、任务状态，则需要更认真地设计持久化和补偿。

面试标准答案：

> RDB 通过周期性快照持久化，文件紧凑、恢复较快，但可能丢失两次快照间的数据；AOF 记录写命令，数据完整性通常更好，但文件更大、恢复成本更高。实际项目可以结合使用，具体取决于 Redis 数据能否重建以及业务允许的数据丢失范围。

------

# 二十一、持久化后，Redis 能代替 MySQL 吗？

通常不能。

即使开启 RDB 和 AOF，Redis 仍然不擅长：

- 复杂关联查询；
- 大量关系型数据；
- 完整事务业务；
- 长期低成本保存海量数据；
- 复杂统计与报表；
- 订单、支付等核心事实记录。

Redis 持久化的含义是：

> 提升 Redis 数据的恢复能力。

不是：

> Redis 从此变成 MySQL。

必须背：

> **持久化解决数据恢复问题，不改变 Redis 主要作为缓存和高速数据结构服务的定位。**

------

# 二十二、什么是热 Key？

热 Key 是指：

> 某一个 Key 的访问量远高于其他 Key。

例如热门药品：

```redis
# 大量用户同时访问同一个热门药品缓存
GET medicine:detail:5001
```

其他药品每秒访问十次，而它每秒访问十万次。

这就是热 Key。

------

## 热 Key 有什么风险？

即使 Redis 整体性能很强，所有请求集中访问一个 Key，也可能导致：

- 单个 Redis 节点压力过大；
- 网络带宽成为瓶颈；
- 热点 Key 过期时发生缓存击穿；
- 集群中负载分布不均；
- 接口延迟上升。

可以想象：

> 商场有一百个收银台，但十万人全部挤在同一个收银台前。

------

# 二十三、热 Key 怎么处理？

## 方案一：本地缓存

把极热点且短期允许不一致的数据，缓存在 Node.js 服务本地。

```js
// 创建服务进程内的本地缓存
const localCache = new Map();

// 将热门药品数据放入本地缓存
localCache.set(
  'medicine:detail:5001', // 本地缓存 Key
  {
    id: 5001, // 药品 ID
    name: '热门药品', // 药品名称
  },
);
```

请求可以先读本地内存，减少 Redis 压力。

缺点：

- 多个服务器数据不一定一致；
- 服务重启会丢失；
- 更新和失效更复杂。

------

## 方案二：拆分热点 Key

可以把一个热点 Key 复制成多个副本：

```text
medicine:detail:5001:copy:1
medicine:detail:5001:copy:2
medicine:detail:5001:copy:3
```

请求随机访问不同副本，分散压力。

这种方案增加了一致性维护成本，了解思想即可。

------

## 方案三：热点永不过期或提前刷新

避免热点 Key 突然失效，造成缓存击穿。

例如：

- 逻辑过期；
- 后台异步刷新；
- 活动前缓存预热。

------

## 方案四：限流与降级

流量异常时：

- 限制接口访问频率；
- 返回兜底数据；
- 暂停非核心推荐功能。

------

# 二十四、什么是大 Key？

大 Key 不是指 Key 的名字很长。

它通常是指：

> 一个 Key 对应的 Value 体积非常大，或者集合中的元素数量非常多。

例如：

```text
一个 String 保存了 20MB JSON
一个 List 有 500 万条消息
一个 Set 有 100 万个用户 ID
一个 Hash 有几十万个字段
```

这些都可能属于大 Key。

------

# 二十五、大 Key 有什么危害？

## 占用大量内存

一个 Key 就吃掉很大一部分 Redis 内存。

## 操作时间长

一次读取或删除大 Key，可能阻塞命令执行。

例如：

```redis
# 删除一个元素数量极多的大集合，可能产生明显耗时
DEL article:all_user_actions
```

## 网络传输压力大

一次 `GET` 返回十几 MB 数据，会占用网络带宽。

## 数据迁移困难

Redis 集群扩容、迁移槽位时，大 Key 传输成本高。

## 过期删除可能产生卡顿

超大 Key 到期或被删除时，释放大量内存也可能带来延迟。

------

# 二十六、如何避免大 Key？

## 1. 拆分数据

不要把所有用户订单放进一个集合：

```text
不推荐：
orders:all_users
```

可以按用户拆分：

```text
orders:user:1001
orders:user:1002
orders:user:1003
```

也可以按日期拆分：

```text
orders:2026:07
orders:2026:08
```

------

## 2. 不要缓存巨大完整对象

TripStar AI 的完整行程可能包含：

- 每日行程；
- 景点；
- 酒店；
- 餐饮；
- 预算；
- 地图数据；
- 知识图谱。

不要无脑将所有历史行程塞进同一个 Key。

可以按任务或模块拆开：

```text
trip:plan:3001:overview
trip:plan:3001:days
trip:plan:3001:budget
```

但也不能拆得极端零碎，需要结合读取方式设计。

------

## 3. 分页读取集合

不要一次取出整个大 List：

```redis
# 不推荐：一次获取列表中的全部元素
LRANGE user:1001:messages 0 -1
```

更合理：

```redis
# 分页获取列表中的前二十条消息
LRANGE user:1001:messages 0 19
```

------

## 4. 异步删除大 Key

如果客户端和 Redis 版本支持，可以使用异步释放思路，避免同步删除长时间阻塞。

```redis
# 异步解除 Key 与数据的关联，并在后台释放内存
UNLINK article:all_user_actions
```

简单理解：

```text
DEL：可能当场清理
UNLINK：先让 Key 不可见，再后台释放
```

但不要看到所有 Key 都机械替换成 `UNLINK`，应根据数据规模和环境选择。

------

# 二十七、热 Key 和大 Key 的区别

## 热 Key

问题是：

> 访问次数太多。

即使 Value 很小，也可能是热 Key。

例如：

```text
system:config
```

只有 1KB，但每秒访问十万次。

## 大 Key

问题是：

> 单个 Value 太大或元素太多。

即使一天只访问一次，也可能造成明显卡顿。

一句话：

> **热 Key 是人太多，大 Key 是东西太重。**

# 二十九、本章必须背的七段答案

## 1. Redis 为什么快？

> Redis 主要在内存中操作数据，内部数据结构经过优化，核心命令执行路径简单，并通过事件驱动和 IO 多路复用处理大量连接。命令执行主要保持顺序性，减少了线程切换和锁竞争。

## 2. Redis 如何删除过期 Key？

> Redis 通常结合惰性删除和定期删除。惰性删除是在访问 Key 时检查是否过期，定期删除则周期性抽样清理过期数据。

## 3. 内存满了怎么办？

> Redis 会根据 maxmemory-policy 处理，可以拒绝新写入，也可以按照 LRU、LFU、随机或剩余 TTL 等规则淘汰部分 Key。

## 4. RDB 是什么？

> RDB 是在某个时间点生成 Redis 数据快照，文件紧凑、恢复较快，但可能丢失两次快照之间的数据。

## 5. AOF 是什么？

> AOF 会追加记录 Redis 的写命令，数据完整性通常更好，但文件更大，恢复时需要重放命令，并需要通过重写控制文件体积。

## 6. 什么是热 Key？

> 热 Key 是访问频率远高于其他 Key 的数据，可能造成单节点压力集中和缓存击穿。可以通过本地缓存、Key 副本、提前刷新和限流等方式缓解。

## 7. 什么是大 Key？

> 大 Key 是 Value 体积很大或集合元素数量很多的 Key，可能导致内存占用过高、网络阻塞、删除卡顿和集群迁移困难。可以通过拆分、分页读取和异步删除等方式优化。

# 三十一、本章闯关题

## 第 1 题

Redis 是不是因为完全只有一个线程才快？

答案：

> 不是。Redis 快与内存操作、高效数据结构、简单命令路径和 IO 多路复用有关。核心命令执行主要保持顺序性，但 Redis 的持久化、网络 IO 等工作不一定只有一个线程。

------

## 第 2 题

Key 过期后是否一定立刻从内存消失？

答案：

> 不一定。Redis 通常通过惰性删除和定期删除清理过期 Key，逻辑过期后可能暂时仍占用内存。

------

## 第 3 题

LRU 和 LFU 有什么区别？

答案：

> LRU 优先淘汰最近最少使用的数据，主要关注最近访问时间；LFU 优先淘汰访问频率最低的数据，主要关注访问次数。

------

## 第 4 题

RDB 和 AOF 最简单的区别是什么？

答案：

> RDB 像定期拍快照，AOF 像持续记录写操作日志。

------

## 第 5 题

热 Key 和大 Key 有什么区别？

答案：

> 热 Key 是访问量太集中，大 Key 是单个 Value 太大或集合元素太多。

------

## 第 6 题

Redis 已经开启持久化，能否代替 MySQL 保存核心订单？

答案：

> 通常不能。持久化只是增强 Redis 的恢复能力，订单仍需要 MySQL 的关系查询、事务一致性和长期可靠存储能力。
